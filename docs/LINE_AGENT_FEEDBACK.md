# สถานะรับข้อความและการตรวจ LINE Agent

อัปเดต 29 ตุลาคม 2026 อ่านคู่กับ [LINE_AGENT.md](LINE_AGENT.md) และ [VERIFICATION.md](VERIFICATION.md)

## เหตุการณ์ที่พบจริง

ข้อความ “วันนี้จะพาน้องพีโอนีไปหยอดหลังคอเพื่อจัดการไรหู” ได้รับวันที่ 29 ตุลาคม 2026 เวลา 12:18 น. ตามเวลาประเทศไทย การตรวจฐานข้อมูลแบบอ่านอย่างเดียวยืนยันว่า:

- `agent.normalize` สำเร็จและเลือก `chat`
- `assistant.chat` สำเร็จ จากนั้นตัวกรองคำตอบเรื่องยาเปลี่ยนคำตอบเป็นข้อความสำรอง
- LINE delivery สถานะ `sent` โดยข้อความตรงกับข้อความสำรองที่ผู้ใช้รายงาน
- ไม่มี Agent task และไม่มีไดอารี่ใหม่ในช่วงเวลาของข้อความนี้

การเลือก Chat ถูกต้องสำหรับข้อความที่เล่าแผนและยังไม่สั่งบันทึก ปัญหาคือ guard ที่เคยจับข้อความอย่าง “ให้คุณหมอประเมินเรื่องยา” กว้างเกินไป และ fallback นำรายการอาการฉุกเฉินมาแสดงแม้เจ้าของไม่ได้รายงานอาการเหล่านั้น ไม่เก็บคำตอบดิบก่อนกรองใน audit จึงไม่อ้างว่าทราบทุกคำในร่างที่โมเดลสร้าง

## พฤติกรรมที่แก้ไข

- แยกการเล่าแผนไปพบหมอออกจากการรักษาที่เกิดขึ้นแล้ว และไม่สร้างไดอารี่โดยไม่ได้รับคำขอ
- ยอมรับข้อความส่งต่อให้สัตวแพทย์ประเมินโดยไม่เหมารวมเป็นคำแนะนำใช้ยา ขนาดยา คำสั่งให้ยาเอง และคำวินิจฉัยฟันธงยังถูกตรวจ
- เมื่อ draft ถูกกรอง ข้อความตอบสำรองต้องสัมพันธ์กับข้อความเจ้าของ อาการฉุกเฉินจริงยังใช้เส้นทางฉุกเฉินเดิม
- หลังรับคำสั่งที่เข้าคิวแล้ว แสดงข้อความรับแล้ว/กำลังประมวลผล และ native loading animation; ข้อความนี้ไม่ใช่การรับรองว่างานสำเร็จ
- ส่งคำถามที่ยังขาดเป็นการ์ด กดตัวเลือกหรือพิมพ์ตอบได้ เมื่อบันทึกสำเร็จจึงส่งปุ่ม LIFF ของผลจริง

## Loading และอ่านแล้วของ LINE

ใช้ endpoint เดิมของ Messaging API และ credentials เดิม ไม่เพิ่ม SQL หรือ env:

- `POST /v2/bot/chat/loading/start` ระบุ `chatId` ของแชทส่วนตัวและ `loadingSeconds=60`
- `POST /v2/bot/chat/markAsRead` ระบุ `message.markAsReadToken` จาก webhook ที่ตรวจลายเซ็นและบันทึกสำเร็จแล้ว

Loading เป็นหน้าตาของ LINE ปรับข้อความหรือปุ่มบน animation เองไม่ได้ จึงแยกข้อความรับแล้วออกจาก animation มันแสดงเฉพาะตอนผู้ใช้เปิดแชทและหายเมื่อมีข้อความใหม่หรือครบเวลา การต่ออายุไม่ทำเป็น timer ที่ทำงานค้างหลังคำขอสิ้นสุด

หาก OA เปิด **Chat** ให้ใช้ read token เพื่อทำเครื่องหมายอ่านแล้ว หากปิด Chat LINE จะอ่านให้อัตโนมัติอยู่แล้ว การไม่มี token ใน event ไม่ใช่เหตุให้สร้าง token เอง ความล้มเหลวของ feedback ไม่ยกเลิกคิวงานหรือส่ง Push ซ้ำแทน reply token ที่หมดอายุ

อ้างอิง [LINE loading animation](https://developers.line.biz/en/docs/messaging-api/use-loading-indicator/) และ [LINE mark as read](https://developers.line.biz/en/docs/messaging-api/mark-as-read/)

## วิธีทดสอบกับบัญชีจริง

1. ส่งข้อความเล่าแผนเดิม ควรตอบรับตรงบริบท ไม่อ้างว่ารักษาแล้วหรือบันทึกแล้ว
2. ต้องการทดสอบการถามเพิ่ม ให้ส่ง “ช่วยบันทึกไดอารี่ของพีโอนีให้หน่อย เดี๋ยวฉันเล่ารายละเอียดในข้อความถัดไป”
3. ตอบการ์ดด้วยเหตุการณ์จริง ระบุชัดว่าเป็นแผนหรือเกิดขึ้นแล้ว ข้อมูลที่ไม่ทราบไม่ต้องเดา
4. รอข้อความกำลังทำงานและผลสำเร็จ เปิดปุ่ม LIFF แล้วตรวจน้อง ข้อความ วันที่ และจำนวนบันทึก

ดูเพิ่มเรื่องแก้/ลบใน [RECORD_MUTATIONS.md](RECORD_MUTATIONS.md) ผลทดสอบจำลองไม่แทนการส่ง/เปิดข้อความใน LINE ของผู้ใช้จริง

## หลักฐานสำหรับนักพัฒนา

ตรวจ durable state ของ `assistant.agent_turns`, `agent_tasks`, `agent_tool_calls`, `agent_deliveries` และ metadata ใน `ai_ops.requests` โดยจำกัดเฉพาะบัญชี/เหตุการณ์ที่ตรวจอยู่ ไม่พิมพ์ LINE user ID, token, รูป, บทสนทนา หรือข้อมูลสุขภาพลง runtime log

Runtime stage logs ใช้ reference ที่ hash แล้วเพื่อเชื่อม normalize → คำถาม → คิว → tool → ผล/ส่งข้อความ และการขอเปิดผลที่ผ่านการตรวจสิทธิ์ การมี log ส่งสำเร็จยืนยันว่า LINE API รับการส่ง ไม่ใช่หลักฐานว่าผู้ใช้เปิดอ่าน; การขอผลจาก LIFF ยืนยัน API access แต่การแสดงผลจริงยังตรวจในหน้าจอผู้ใช้
