# วันที่ค่าใช้จ่ายแบบไม่บังคับ

ค่าใช้จ่ายแต่ละรายการในไดอารี่ดูแลน้องมี **วันที่รายการ / Expense date** แยกจากวันที่ของไดอารี่ และใช้ได้กับผลหลังพบหมอจาก Pet Passport ด้วย เช่น เหตุการณ์วันที่ 29 แต่จ่ายวันที่ 30 สามารถเก็บสองวันนี้แยกกันได้

- เว้นวันที่ว่างได้ ไม่มีการเติมวันนี้หรือวันเกิดเหตุการณ์ให้อัตโนมัติ
- รายการเก่ายังคงไม่มีวันที่จนกว่าเจ้าของจะเลือกเพิ่มเอง
- แก้ไขหรือล้างวันที่ได้ โดยยังรักษายอด สกุลเงิน และการแยกจ่ายจริง/ประมาณการ
- ประวัติ สรุป/พิมพ์สำหรับคุณหมอ และ export แสดงวันที่ที่เจ้าของระบุ วันที่ค่าใช้จ่ายแชร์ได้เฉพาะขอบเขตค่าใช้จ่ายที่อนุญาตเดิม
- LINE Agent ใช้ `costs.expenseDate` เมื่อเจ้าของบอกวันที่รายการชัดเจน ไม่เดาจากวันบันทึก เมื่อแก้รายละเอียดอื่นต้องรักษาวันที่เดิมไว้

ค่าใช้จ่ายอยู่คู่กับบันทึกการดูแลที่เกี่ยวข้อง ยอดรวมแยกตามสกุลเงินและจ่ายจริง/ประมาณการ

## รูปแบบข้อมูล

API ใช้ `expenseDate: "2026-10-30"` หรือ `null` เป็นวันที่ Gregorian ล้วน `YYYY-MM-DD` ไม่ใช่ timestamp และไม่แปลงเวลา รายการที่ไม่ส่ง field จะได้ค่า `null`

```json
{
  "label": "ค่าตรวจ",
  "amountMinor": 55000,
  "currency": "THB",
  "kind": "paid",
  "expenseDate": "2026-10-30"
}
```

ตรวจวันตามปฏิทินจริงและปี 0001–9999 เช่น `2026-02-30` ใช้ไม่ได้ วันว่างไม่ถือว่าเป็นศูนย์หรือวันของเหตุการณ์ การคิดเงินยังใช้หน่วยย่อยจำนวนเต็ม ตัวอย่าง 550 บาทคือ `amountMinor=55000`

## SQL รุ่น 24

Migration [`202610290024_expense_dates.sql`](../supabase/migrations/202610290024_expense_dates.sql) เพิ่ม `health.care_costs.expense_date DATE NULL` และปรับ projection สรุปคลินิก ไม่แก้ migration รุ่น 1–23 ไม่ backfill วันที่เดิม และไม่ขยายสิทธิ์แชร์

ผู้ดูแลที่จัดการ SQL เองรัน [`diagnostic.sql`](../supabase/diagnostic.sql) → [`upgrade.sql`](../supabase/upgrade.sql) → diagnostic อีกครั้ง ฐานที่มีข้อมูลแล้วไม่ใช้ bootstrap ซ้ำ ไม่เพิ่มหรือเปลี่ยน env สำหรับส่วนนี้ Fingerprint รุ่น 24 คือ `920e7c3673511ed3914d17fc6f094a71`

โค้ด backend ยังรองรับรายการที่ไม่ใส่วันที่บน schema 23 หากมีวันที่แต่ฐานยังไม่รองรับ จะตอบ `EXPENSE_DATES_UPGRADE_REQUIRED` และ rollback ไม่ทิ้งวันที่หรือบันทึกข้อมูลเพียงบางส่วน UI เก็บร่างให้แก้หรือลองใหม่ ควรอัปเกรดก่อนเปิด UI รุ่นนี้ให้ผู้ใช้จริง

คำขอสร้างเก่าที่ไม่เคยมี field วันที่ยัง retry ได้ด้วย hash เดิม เพราะ `null`/field ที่ไม่ส่งถูกละออกจาก canonical hash เฉพาะส่วนวันที่ ค่า date ที่ระบุจริงเป็นส่วนหนึ่งของ request identity และการเปลี่ยนวันต้องแก้รายการปัจจุบันตาม version

Agent รักษา raw HTTP idempotency key ของคำขอก่อนเพิ่ม field ด้วยการละ date ที่เป็น null/ไม่ส่งในสาม tools ค่าใช้จ่าย ก่อนเรียก API ส่วนวันที่ที่ระบุจริงยังส่งครบ Backend แปล field ที่ไม่ส่งเป็น null ตาม schema จึงยังล้างวันที่ตามคำขอได้

Trigger รุ่น 23 ยกเลิกสรุป/Passport ที่อ้างข้อมูลค่าใช้จ่ายเมื่อวันที่เปลี่ยนอยู่แล้ว วันที่จึงไม่ทำให้ลิงก์ที่มีข้อมูลเก่ากลายเป็นข้อมูลปัจจุบันโดยเงียบ ๆ

## ตรวจการทำงาน

ทดสอบทั้งรายการไม่ใส่วันที่ วันที่ต่างจากวันไดอารี่ วันที่ปฏิทินผิด แก้และล้างวันที่ retry ไม่สร้างซ้ำ และอ่าน/แชร์เฉพาะขอบเขตที่อนุญาต รวมถึงทดสอบ API รุ่นใหม่กับฐาน 23 แยกเพื่อยืนยันว่า dated request ล้มเหลวโดยข้อมูลเดิมไม่เสีย รายละเอียดผลล่าสุดอยู่ใน [VERIFICATION.md](VERIFICATION.md)
