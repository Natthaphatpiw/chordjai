# ChordJai: ฟีเจอร์และขอบเขตที่ส่งมอบ

## LINE Agent — เตรียมในโค้ด local 29 ตุลาคม 2026

เจ้าของสั่งงานในแชทส่วนตัวกับ LINE OA เช่น “วันนี้พาน้องถั่วเหลืองไปหยอดหลังคอกำจัดไรหูมา บันทึกไว้ให้หน่อย” ได้ LLM0 classify/normalize แล้วส่งคำถามทั่วไปเข้า AI Chat เดิม หรือส่งคำสั่งให้ Agent อ่านข้อมูลที่จำเป็นและทำงานผ่าน API เดิม ถ้าข้อมูลจำเป็นไม่ครบจะถามด้วยการ์ด กดตอบหรือพิมพ์เองได้ เมื่อพร้อมจะรับทราบว่ากำลังทำงาน แล้วส่งผลและลิงก์ LIFF ไปยังรายการที่เกี่ยวข้อง

- มี **48 tools: อ่าน 22, สร้าง 10, ต้องยืนยัน 16** ครอบคลุมโปรไฟล์ สมุดสุขภาพ ไดอารี่/เรื่องการดูแล เตือน ความทรงจำ คลินิก/นัดหมาย Passport สถานะ PetID ประกาศหาย ลิงก์สุขภาพ และ memory ที่เปิดรับ
- สร้างรายการจากคำสั่งชัดเจน งานแก้ข้อมูลเดิม ลบ memory ส่งคำขอนัด หรือเผยแพร่ประกาศต้องตรวจยืนยัน แยกเจ้าของ งาน รุ่นของแผน และตัวสัตว์ก่อนทำ ไม่เดาข้อมูลยา ราคา วันนัด หรือการหายจากอาการ
- ความยินยอม สิทธิ์คลินิก การอนุมัติฝึก PetID การยืนยันตัวตน biometrics การยืนยัน Passport ฉบับเต็ม สร้างลิงก์แชร์ อัปโหลดรูป และตรวจร่างจัดหน้า AI ยังทำใน LIFF ไม่ถือว่ากด “yes” ในแชทเป็นการยินยอมทั้งหมด
- เก็บงาน/คำถาม/outbox ในฐานข้อมูลเพื่อคุยต่อและ retry ด้วย key เดิม ตรวจสิทธิ์ใหม่ก่อนทำและส่งผล ใช้ `gpt-6.1-sol` ผ่าน client กลางเดิม ไม่เพิ่ม framework โมเดล repo หรือบริการใหม่

**สถานะ:** เตรียม migration **22** และ env example พร้อมแล้ว โดย `LINE_AGENT_ENABLED=false` เป็นค่าเริ่มต้น ยังไม่ได้รัน SQL ใน Supabase จริง ตั้ง env จริง deploy หรือส่งข้อความทดสอบจริง ผู้ดูแลจะรัน SQL/ตั้ง env เอง หลักฐาน production ล่าสุดยังเป็น schema **21** การเปิดใช้ต้องตรวจฐานข้อมูลและ backend/owner app ให้ตรงรุ่นก่อน รายละเอียด flow, tools, API, privacy และขั้นตอนเปิดใช้ใน [LINE_AGENT.md](LINE_AGENT.md)

Agent ช่วยลดขั้นตอนการกลับมาจดข้อมูลของ core diary เป็นสมมติฐานด้าน activation/recurring ที่ต้องวัดกับผู้ใช้จริง ไม่ใช้จำนวนข้อความหรือจำนวน tools แทน retention หรือคุณภาพข้อมูล

## Pet Passport Q&A — 13 ตุลาคม 2026

ต่อยอด **เตรียมพบคุณหมอ** ในสมุดสุขภาพเป็นบทสนทนารายครั้ง ถามต่อจากคำตอบจริง เปลี่ยนคำถามเมื่อไม่ทราบ และเก็บความไม่รู้ตามจริง ร่างเป็นของเจ้าของน้อง เก็บคำตอบแต่ละฉบับพร้อมเวลาและป้องกันการบันทึกทับ

เจ้าของตรวจ/แก้คำตอบ ประวัติและรูปที่เลือก แล้วกดยืนยันก่อนสร้างลิงก์อายุ 1–14 วันหรือเปิดให้คลินิกที่มีสิทธิ์ `passport.read` หมออ่านสรุปสำคัญแล้วเปิด Q&A และรูปต่อได้ การเพิ่มบันทึกจากสัตวแพทย์ต้องมี `passport.write` แยก เจ้าของตรวจผลอีกครั้งก่อนลงไดอารี่ เรื่องการดูแลและวันเตือน ใช้ LINE follow-up เฉพาะเมื่อเลือกเปิดและอนุญาตไดอารี่ไว้แล้ว

ใช้ migration 21 ไม่เพิ่ม repo/project/env/LIFF endpoint ไม่มีการส่งรูปเข้า AI นี้หรือฝึก PetID อัตโนมัติ การแก้/ถอนสิทธิ์/ลบต้นทางปิดฉบับที่แชร์เดิม งาน AI เลือกได้เฉพาะรหัสคำถามที่ควบคุม และมีกฎรองรับเมื่อ AI ไม่พร้อม ยังต้องประเมินประโยชน์และความปลอดภัยกับสัตวแพทย์จริง ดู [PET_PASSPORT.md](PET_PASSPORT.md)

## ตรวจภาพ / หลักฐาน / pipeline PetID และรูปไดอารี่ — 12 ตุลาคม 2026

- เจ้าของเลือกตรวจภาพที่บันทึกไว้: ขนาด แสง ความคมชัด ภาพซ้ำ และความสอดคล้องด้วย `gpt-6.1-sol` โดยเลือกอนุญาตส่งภาพก่อน ผลไม่อ้างว่า AI พิสูจน์ตัวตน
- ผู้ตรวจอิสระในแอดมินระบุหลักฐานสแกนไมโครชิป บันทึกคลินิก หรือชุดอ้างอิงที่ทบทวนแล้ว ห้ามอนุมัติสัตว์ตัวเอง ทุกภาพต้องผ่านตรวจรุ่นปัจจุบันและความยินยอมยังมีผล
- Manifest วิจัยอายุ 24 ชั่วโมง ใช้คำแทนเจ้าของ/น้องแทนชื่อ ไม่มีลิงก์ภาพหรือข้อมูลรักษา การถอนสิทธิ์/ลบภาพ/แก้ผลตรวจทำให้ snapshot เดิมใช้ต่อไม่ได้
- Pipeline ท้องถิ่นฝึก CNN embedding ได้จริง แบ่งชุดตามเจ้าของ/สัตว์/วัน/ชุดถ่าย ตรวจภาพซ้ำ ตั้ง threshold ด้วย calibration แล้วรายงาน FMR/FNMR, rank-1/rank-5, FPIR/FNIR และช่วงความเชื่อมั่น โมเดลไม่เปิดใช้จริงอัตโนมัติ ผลข้อมูลสังเคราะห์ไม่ใช่ความแม่นยำกับสัตว์จริง
- ไดอารี่แสดงปุ่มถ่ายและแนบภาพใกล้เรื่องเล่า สูงสุด 5 รูป พร้อมดูเต็มภาพ แก้ไข/เก็บรูปเดิม และ retry เฉพาะรูปที่ค้างด้วยคำขอเดิม ไม่ส่งภาพไดอารี่ให้ AI/คลินิก/PetID หรือฝึกอัตโนมัติ

รายละเอียด [PETID_DATASET.md](PETID_DATASET.md) และ [PETID_MODEL_PIPELINE.md](PETID_MODEL_PIPELINE.md) ใช้ migrations 19–20 เพิ่มจากรุ่นเดิม ไม่มี repo หรือ LIFF endpoint ใหม่ Python research runtime แยกจาก Vercel

อ้างอิง `SYSTEM_DESIGN.md` และ `REQUIREMENTS_ANALYSIS.md` โดยถือว่าเป็นรายละเอียดระบบ ผู้ใช้แก้ข้อกำหนดเพิ่มเติมให้มีสมุดที่ตกแต่งได้เอง/ด้วย AI, AI chat พร้อม memory และใช้ `gpt-6.1-sol` เป็นค่าเริ่มต้นของงานสร้างข้อความและอ่านภาพ


## คลังภาพ PetID และ LINE follow-up แบบเลือกเปิดรับ — 12 ตุลาคม 2026

- คลังภาพแยกจากทะเบียนค้นหาสัตว์หาย เก็บ 1–5 รูปต่อชุด พร้อมมุม วันถ่ายที่เจ้าของระบุและเวลาอัปโหลดจริง กลับมาเพิ่มชุดต่างเวลาได้ ยืนยันตัวเดิมเป็น owner attestation พร้อม identity anchor ที่ยังไม่ยืนยันอิสระ
- ความยินยอม `petid_model_training` แยกเฉพาะน้องแต่ละตัวและมี revision/history ค่าเริ่มต้นปิด เก็บภาพได้แม้ไม่ยินยอมฝึก ถอนสิทธิ์แล้วชุดเดิมหมดสิทธิ์ตาม revision เดิม; การเปิดใหม่ต้องทบทวนใหม่ ทุกชุดใหม่รอตรวจ ไม่มีการอนุมัติ/ส่งออก/ฝึกอัตโนมัติ
- ตั้งค่า LINE follow-up แยกจาก marketing และ memory: ปิดและไม่เลือกแหล่งข้อมูลไว้ก่อน เลือก 5/7 วัน ภาษาและพักได้ เลือก care/booklet/journal/approved assistant memory ทีละส่วนและยินยอม AI ก่อนเปิด
- หลังเปลี่ยนตัวเลือกเว้นอย่างน้อย 24 ชั่วโมงก่อนส่งอัตโนมัติ ส่งเฉพาะ 09:00–20:00 Bangkok, เคารพ cadence ต่อผู้ใช้แม้มีหลายสัตว์, ให้ reminder ตามกำหนดก่อน และข้ามได้เมื่อไม่มีเรื่องเหมาะสม/มีคำตอบแล้ว เรื่องเดิมที่เงียบถูกถามได้ไม่เกินสองครั้งต่อรุ่นข้อมูล
- LLM เลือกแหล่งข้อมูล หัวข้อ คำถามและโทนที่มีขอบเขต ข้อความประกอบด้วยชื่อ/วันจริงจากแหล่งที่มีสิทธิ์ หัวข้อหูจากบันทึกความทรงจำถามอาการเกาหู/สะบัดหัวได้ แต่ไม่วินิจฉัยหรือเปลี่ยนยา ไม่ใช้ความรู้สึกส่วนตัว ค่าใช้จ่าย รูป หรือประวัติแชทเต็ม
- ปุ่มดูตัวอย่างไม่ส่ง LINE; ส่งจริงด้วย Push API และ webhook เดิมรับ PAUSE/RESUME/คำตอบ คำตอบเป็นข้อมูลส่วนตัวที่ยังไม่ยืนยันความเกี่ยวข้องและไม่สร้างเวชระเบียนอัตโนมัติ ข้อความ/คำตอบลบหลัง 90 วัน
- Admin เห็นตัวนับชุดภาพต่างวัน ความยินยอม และคำขอ LINE ที่รับ/เปิดลิงก์/ตอบ โดยไม่เห็นภาพหรือข้อความผู้ใช้ จำนวนเหล่านี้ยังไม่ใช่ความแม่นยำ/retention ที่พิสูจน์เหตุและผล

รายละเอียดใน [PETID_DATASET.md](PETID_DATASET.md) และ [PERSONALIZED_FOLLOWUPS.md](PERSONALIZED_FOLLOWUPS.md). ใช้ migrations 17–18 พร้อม safe upgrade; ไม่มี repo, LIFF endpoint หรือ env ใหม่

## Core product ปัจจุบัน: ไดอารี่ดูแลน้อง — 12 ตุลาคม 2026

**ไดอารี่ดูแลน้องเป็นหน้าเริ่มต้นของสมุดสุขภาพ** เจ้าของเริ่มจากเล่าว่า “วันนี้น้องเป็นอย่างไร” ได้ทั้งวันปกติ วันที่มีอาการ ไปพบหมอ และติดตามหลังรักษา หน้าหลักมีปุ่มเริ่มบันทึกและเรื่องล่าสุด ส่วนสมุดประจำตัว/วัคซีนยังอยู่ในสมุดสุขภาพอีกมุมหนึ่ง สมุดความทรงจำเป็นพื้นที่สร้างหน้า Story จากสิ่งที่เจ้าของเลือกเก็บ

| ช่วงการดูแล | ฟีเจอร์ที่มี | ข้อมูลและคุณค่าที่ได้รับ |
|---|---|---|
| เล่าเรื่องของวันนี้ | ข้อความก่อน แล้วค่อยเพิ่มรูปได้สูงสุด 5 รูป/วันที่/อาการ/ความรุนแรง/การกิน/ดื่ม/พลังงาน/ขับถ่าย | เก็บบริบทที่บ้านอย่างต่อเนื่อง ช่องที่ไม่ทราบคงเป็นไม่ทราบ ไม่ถือว่าวันที่ไม่บันทึกแปลว่าน้องปกติ |
| ดูแลเรื่องเดิมต่อ | รวมบันทึกเป็นเรื่องการดูแล เพิ่มอัปเดตและเปลี่ยนสถานะกำลังดูแล/ดีขึ้น/ปิดเรื่อง | เห็นลำดับตั้งแต่เริ่มอาการ การเปลี่ยนแปลง ไปพบหมอ จนผลหลังรักษา |
| ไปพบคุณหมอ | ชื่อคลินิก เหตุผล สิ่งที่เจ้าของรายงานว่าหมอบอก การรักษา/คำแนะนำ และวันติดตาม | ข้อมูลติดป้ายว่าเจ้าของรายงาน การพิมพ์คำวินิจฉัยไม่เปลี่ยนเป็นการยืนยันจากสัตวแพทย์ |
| จดค่ารักษา | รายการและจำนวนที่ทราบ แยกจ่ายจริง/ประมาณการ และ THB/USD | เก็บจำนวนเป็นหน่วยย่อยของสกุลเงิน ไม่รวมต่างสกุลหรือประมาณการเป็นยอดจ่ายจริง ค่าไม่ทราบต่างจากศูนย์ |
| พื้นที่ระบาย | ความรู้สึกส่วนตัวแยกจากเรื่องเล่าและข้อความสำหรับคุณหมอ | ความรู้สึกเห็นได้เฉพาะผู้เขียน ไม่เปิดให้คนในบ้าน คลินิก สรุปสาธารณะ หรือบริบท AI อัตโนมัติ |
| เตรียมไปพบหมอ | ข้อความสำหรับคุณหมอแยกจากเรื่องเล่า เลือกอนุญาตแชร์เป็นรายบันทึก ดูสรุปและเลือกแถวดาวน์โหลด TXT | ส่งต่อข้อสังเกตที่เลือก โดยไม่ส่งเรื่องเล่าเต็ม ความรู้สึกส่วนตัว หรือรูปไดอารี่ |
| เก็บเป็นความทรงจำ | เลือกข้อความและรูปจากบันทึก แล้วเปิดร่างหน้า Story ที่แก้ไขได้ | สร้างความทรงจำด้วยการเลือกของเจ้าของ ต้องตรวจและบันทึกหน้าเอง ไม่มีการสร้างหน้าหรือเผยแพร่อัตโนมัติ |

วันติดตามที่เจ้าของเลือกสร้าง reminder ให้ผู้เขียนบันทึก ใช้รายการเดิมเมื่อแก้ไขและไม่เตือนซ้ำเพียงเพราะแก้ข้อความ การอนุญาตคลินิกอ่านข้อมูลไม่ได้ส่งแจ้งเตือนไปคลินิก และไม่ได้หมายความว่าคลินิกกำลังติดตามอาการทันที

**ประวัติไดอารี่ไม่มีเพดานจำนวนบันทึก** หน้าไทม์ไลน์โหลดรายการเก่าต่อด้วย keyset pagination ครั้งละ 50 รายการ (API รองรับสูงสุด 200 ต่อคำขอ) และเรื่องการดูแลโหลดเก่าต่อได้เช่นกัน เวลา cursor เก็บความละเอียดของ PostgreSQL เพื่อไม่ข้ามบันทึกที่เวลาใกล้กัน ส่วนไดอารี่ในสรุปคลินิก/ลิงก์แชร์จำกัด **100 บันทึกล่าสุดที่อนุญาตแชร์ไว้** พร้อมระบุเมื่อยังมีรายการอื่น เกณฑ์นี้ไม่ใช่เพดานการเก็บประวัติ

การเลือกแถวในหน้าสรุปมีผลกับไฟล์ TXT ที่ดาวน์โหลดเท่านั้น ลิงก์สาธารณะมีขั้นตอนเลือกไดอารี่/ค่าใช้จ่ายแยก และรวมรายการที่เข้าเงื่อนไขล่าสุด ไม่ใช้ตัวกรองเรื่องการดูแลจากไทม์ไลน์เป็นตัวกรองสรุป ข้อมูลช่วงวันหรือรายเรื่องในรายงานเป็นงานถัดไป

ลิงก์สรุปยังมีโปรไฟล์และระเบียนสมุดสุขภาพเดิมสูงสุด 100 รายการพร้อมหมายเหตุของระเบียนนั้น ตัวเลือกไดอารี่ไม่ได้เปลี่ยนขอบเขตระเบียนเดิม เจ้าของจึงต้องตรวจทั้งสองส่วนก่อนสร้างลิงก์

คลินิกต้องได้รับสิทธิ์ **`care.read`** แยกจาก `summary.read` และเห็นเฉพาะบันทึกที่เจ้าของเปิดการแชร์ไว้ ค่าใช้จ่ายต้องมีสิทธิ์รายบันทึกและเลือกแสดงค่าใช้จ่ายเพิ่ม การให้สิทธิ์เดิมไม่เปิดไดอารี่เพิ่มเอง ลิงก์สาธารณะเป็น snapshot: การแก้ข้อความปกติไม่แก้ snapshot แต่การลบบันทึกหรือถอนการแชร์บันทึก/ค่าใช้จ่ายเพิกถอนลิงก์ที่มีบันทึกนั้น

เรื่องเล่าอ่านได้ตามสิทธิ์ครอบครัว บันทึกแก้ไขได้โดยผู้เขียนหรือเจ้าของน้อง มี version/ผู้แก้/เวลาแก้และป้องกันการทับฉบับใหม่ ระบบยังไม่ได้เก็บเนื้อหาทุกฉบับย้อนหลังเป็น amendment history ความรู้สึกส่วนตัวแก้ไขได้เฉพาะผู้เขียน การลบบัญชีผู้เขียนลบไดอารี่ ความรู้สึก ค่าใช้จ่ายและการเชื่อมรูปของผู้นั้น ส่วนบันทึกของคนอื่นยังอยู่

AI ใช้บริบททางคลินิกที่จำกัดและระบุว่าเจ้าของรายงาน โดยไม่อ่านเรื่องเล่าเต็ม ความรู้สึก รูป หรือค่าใช้จ่ายจากไดอารี่อัตโนมัติ หลังบ้านมีจำนวนการบันทึก เรื่องที่ติดตาม การไปคลินิกและข้อมูล PetID แบบรวม ไม่มีการนำรูปไดอารี่ไปลงทะเบียน/ฝึก PetID อัตโนมัติ เหตุผลการออกแบบ ข้อมูลอ้างอิง และเส้นทางไปเครื่องมือคลินิก/ธุรกิจ PetID อยู่ใน [CORE_PRODUCT_STRATEGY.md](CORE_PRODUCT_STRATEGY.md)

รอบนี้ใช้ migration `202610120016_care_diary.sql` ฐานข้อมูล Supabase ของโปรเจกต์อัปเกรดและตรวจยืนยันเป็น **รุ่น 16** แล้ว โครง repo, environment และ endpoint LIFF ใช้ค่าเดิม

## ผู้ใช้ได้อะไร

### ปรับโฟลว์สมุดและ PetID — 12 ตุลาคม 2026

- **สแกนสมุดสุขภาพเป็นชุด:** ถ่ายเพิ่มทีละหน้า หรือเลือกรูปหลายหน้า รวมได้ 1–10 หน้า ดูตัวอย่าง ลบและเรียงลำดับได้ก่อนกดประมวลผลครั้งเดียว รูปยังไม่ถูกส่งอ่านด้วย AI ระหว่างสะสมหน้า ผลอ่านระบุหน้าต้นทาง และมีคำอธิบายรวมเป็น bullet points ในกล่องเดียว ตรวจ/แก้วันและรายการก่อนยืนยันบันทึก การส่งซ้ำหลังการเชื่อมต่อขัดข้องไม่สร้างรายการซ้ำ
- **สมุดประจำตัวอ่านง่ายขึ้น:** โปรไฟล์น้อง น้ำหนักล่าสุด วันนัดถัดไป และไทม์ไลน์แยกเป็นส่วนที่มีลำดับชัดเจน แบบตรวจผลสแกนแสดงรูปหน้าต้นทางคู่กับรายการที่แก้ไขได้
- **สมุดความทรงจำ:** เริ่มที่หน้าปกซึ่งแต่งเองหรือสั่ง AI ได้ เปิดอ่านทีละหน้า มีแถบความคืบหน้า/ก่อนหน้า/ถัดไป เพิ่ม แก้ และลบหน้าแยกกัน สมุดเริ่มมีหน้าเดียวได้และเก็บถาวร ไม่หมดอายุใน 24 ชั่วโมง สมุดส่วนตัวแยกตามผู้เขียนและน้อง แม้ผู้เขียนมีสิทธิ์ดูแลน้องร่วมกัน
- **แต่งหน้าแบบ Story:** หน้าใหม่เป็นแนวตั้ง 9:16 เพิ่มรูป ข้อความ สติกเกอร์ วันที่ และสถานที่ ลากย้าย แตะเลือก ย่อ/ขยายด้วยปุ่ม แถบเลื่อน จับมุม หรือใช้สองนิ้ว และหมุนได้ ไม่มีช่องขนาดรูปเป็นตัวเลข หน้าเดิม 800×1000 ยังคงเนื้อหาและตำแหน่งเดิมไว้ ภาษาในส่วนควบคุมสลับได้โดยไม่เปลี่ยนข้อความที่ผู้ใช้เขียน
- **PetID หลายมุม:** อัปโหลดหรือถ่าย 1–5 รูป จากนั้นกดให้ AI ร่างจุดสังเกตเอง ผู้ใช้แก้ข้อความ ตรวจรูป และยืนยันก่อนลงทะเบียน ลำดับ/จำนวนรูปที่เปลี่ยนต้องสร้างร่างใหม่ ระบบเก็บหนึ่งเวกเตอร์จากข้อมูลภาพหลายมุม แล้วตรวจคู่ภาพด้วย LLM เพื่อคัดตัวที่อาจคล้ายกัน เจ้าของยังต้องยืนยันผล เมื่อรูปอ้างอิงถูกลบ ระบบล้าง signature/embedding ที่เคยสร้างจากชุดรูปนั้น
- **เข้าจาก LIFF:** เริ่ม LIFF SDK แลก token ที่ตรวจฝั่ง server แล้วเปิดหน้าหลักอัตโนมัติ ผู้ใช้ที่ยังไม่อนุญาต service consent ยังต้องเลือกยินยอมด้วยตนเอง เบราว์เซอร์ปกติยังมีทางเลือกเข้าสู่ระบบและพื้นที่ตัวอย่าง การออกจากระบบยกเลิกผลการเข้าสู่ระบบที่ยังรออยู่

รอบสมุด/Story/PetID ข้างต้นใช้ migration `202610110015_memory_books_petid_photos.sql` ส่วนไดอารี่ดูแลรุ่นปัจจุบันเพิ่ม migration 16 ฐานข้อมูลเดิมให้ใช้ `supabase/upgrade.sql` ซึ่งตรวจสถานะและเพิ่มเฉพาะ migration ที่ขาด ห้ามรัน bootstrap ซ้ำ

## Key feature ที่ดึงผู้ใช้ใหม่

1. **เล่าเรื่องน้อง → จดอาการ/ไปพบหมอ → เตรียมสรุปที่เลือกแชร์** เจ้าของเริ่มบันทึกได้จากข้อความ แล้วเพิ่มรายละเอียดเมื่อจำเป็น ได้พื้นที่ระบายและประวัติใช้ประกอบการคุยกับหมอในเรื่องเดียวกัน
2. **ถ่ายสมุดวัคซีน → ตรวจร่าง → บันทึก → มีวันเตือน** เป็นคุณค่าแรกที่อธิบายง่ายและแก้ปัญหาของเจ้าของทันที ความไม่ชัดเจนต้องให้เจ้าของตรวจและยืนยัน
3. **สมุดน้องที่ตกแต่งได้** ทำให้การดูแลสุขภาพมีความรู้สึกส่วนตัว ผู้ใช้ลากรูปและสติกเกอร์เอง หรือพิมพ์ว่า “ทำธีมพาสเทลและจัดรูปไว้ด้านซ้าย” แล้วดูร่างก่อนบันทึก
4. **เช็กความเร่งด่วนและข้อมูลฉุกเฉิน** ให้ประโยชน์เวลาผู้ใช้กังวล กฎฉุกเฉินต้องทำงานแม้ AI ใช้ไม่ได้ เป็นการคัดกรองความเร่งด่วน ไม่ใช่การวินิจฉัยหรือสั่งยา
5. **ประกาศน้องหายและสรุปแชร์ก่อนพบหมอ** สร้างทางให้คนภายนอกเข้าถึงคุณค่าของระบบผ่านลิงก์ และกลับมาเริ่มใช้งานเมื่อมีน้องของตัวเอง

PetID เป็นฟีเจอร์ดึงดูดที่ต้องสื่อสารอย่างแม่นยำ: รูปคล้ายกันเป็นเพียง candidate เจ้าของต้องยืนยันทุกครั้ง ยังไม่ใช่หลักฐานยืนยันตัวหรือระบบแทนไมโครชิป

| วงจรบ้าน–คลินิก | ขอเข้าพบ, ให้สิทธิ์สรุป, เตือนรอบถัดไป | ข้อมูลใช้ได้ทั้งก่อนและหลังพบหมอ |

เป้าหมาย activation ใน 7 วัน, retention เดือนที่ 2, ความตรงกับหมอ และงบในเอกสารเป็น **เป้าที่ต้องวัดจริง** ยังไม่มีตัวเลขที่ยืนยันว่า pilot ทำได้แล้ว

ระเบียนในสมุดประจำตัว/วัคซีนเป็นข้อมูลของน้อง เมื่อผู้ดูแลร่วมลบบัญชี ระเบียนที่เคยบันทึกให้น้องของเจ้าของคนอื่นยังอยู่ต่อ โดยลบข้อมูลอ้างอิงผู้บันทึกออก การลบน้องหรือบัญชีเจ้าของน้องจึงค่อยลบระเบียนของน้องนั้น ไดอารี่ดูแลเป็นเนื้อหาของผู้เขียนและลบตามบัญชีผู้เขียนตามขอบเขตที่ระบุข้างต้น

## สมุดตกแต่งสองวิธี

**วิธีที่ 1: ทำเอง** เพิ่ม/เลือกองค์ประกอบ ย้ายตำแหน่ง ปรับสีและข้อความแล้วบันทึกเป็น JSON ของหน้า สมุดแยกจากระเบียนสุขภาพ การย้ายสติกเกอร์จึงไม่เปลี่ยนวันนัดหรือผลคัดกรอง มีเลข `version` เพื่อตรวจการบันทึกทับหน้าเมื่อมีหลายแท็บ

**วิธีที่ 2: สั่ง AI** ส่งคำบอกธีมและโครงหน้าปัจจุบันให้โมเดล คืนร่างที่ผ่าน schema validation เป็นสี/ข้อความ/ตำแหน่ง/สติกเกอร์ที่อนุญาต ผู้ใช้ตรวจร่างและบันทึก ไม่รัน HTML, JavaScript หรือคำสั่งฐานข้อมูลที่โมเดลสร้าง

งาน AI นี้ใช้ config เดียวกับ OCR, chat, triage และ vision ค่าเริ่มต้นคือ `gpt-6.1-sol` หากบัญชี API ไม่รองรับชื่อนี้ต้องแจ้งข้อผิดพลาดชัดเจน ไม่มีการเปลี่ยนไปใช้ LLM เดิมเงียบ ๆ งาน embedding ของ PetID ใช้ `text-embedding-3-small` ซึ่งเป็น API สำหรับเวกเตอร์โดยเฉพาะและแยก config จาก LLM

## Chat และ memory

- เรียก OpenAI API ผ่าน client กลาง ใช้ประวัติจากฐานข้อมูลส่งกลับเป็นบริบทให้โมเดล การตอบต่อเนื่องไม่พึ่ง state ใน process ของ Vercel
- Personality มาจากชื่อผู้ช่วย โทน และคำอธิบายที่ผู้ใช้เลือก ไม่ใช่การปลอมตัวเป็นผู้เชี่ยวชาญหรือเก็บข้อมูลลับ
- Memory แยกจากข้อความสนทนา ผู้ใช้ต้องเปิดใช้เอง และสามารถดู/เพิ่ม/ลบแต่ละรายการหรือปิดทั้งหมด การถอนความยินยอมปิดการใช้ memory ทันที
- ข้อมูลส่วนตัวของผู้ใช้แต่ละคนแยกด้วย RLS ผู้ดูแลร่วมของน้องไม่เห็นแชตหรือ memory ของเจ้าของโดยอัตโนมัติ
- ถ้าปิด memory ประวัติบทสนทนาภายในห้องยังใช้คุยต่อได้ ความจำข้ามห้องจะไม่ถูกนำมาใช้

## Architecture ที่ใช้งานรุ่นนี้

สร้าง **1 Git repository** แล้วเชื่อม **4 Vercel projects**: owner-app, clinic-portal, admin-console และ backend ภายใน backend แยก13บริการเชิงธุรกิจ (11เดิม+ journal+ assistant) และ scheduler งาน retry ใช้คิวทนทานใน PostgreSQL ในรุ่นนี้

Git repository, Vercel project และ service เป็นคนละสิ่ง ไม่ต้องสร้าง repoต่อmicroservice ภายใน pilot แต่ละserviceมีschemaของตัวเองแต่ใช้ roleแอปร่วมกัน การdeployร่วมและFKข้ามschemaช่วยให้คนเดียวดูแลง่ายและลบบัญชีครบ หากต้องการบริการdeployอิสระหรือแยกฐานข้อมูลจริง ต้องทำrole/service contract และevent cleanupเพิ่มตามสถาปัตยกรรมตั้งต้น

เอกสารเดิมมี162API/43topicและแผน16สัปดาห์ โค้ดนี้เป็นpilotที่มีflowหลักใช้งานได้ ไม่ได้อ้างว่างานครบทุกacceptanceในแผนดังกล่าว Testที่ผ่านด้านRLS/queueไม่แทนclinical eval100เคส, reviewจากสัตวแพทย์, load/security test, การซ้อมrestore หรือ legal reviewของPDPA
