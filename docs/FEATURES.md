# ChordJai: ฟีเจอร์และขอบเขตที่ส่งมอบ

อ้างอิง `SYSTEM_DESIGN.md` และ `REQUIREMENTS_ANALYSIS.md` โดยถือว่าเป็นรายละเอียดระบบ ผู้ใช้แก้ข้อกำหนดเพิ่มเติมให้มีสมุดที่ตกแต่งได้เอง/ด้วย AI, AI chat พร้อม memory และใช้ `gpt-6.1-sol` เป็นค่าเริ่มต้นของงานสร้างข้อความและอ่านภาพ

## ผู้ใช้ได้อะไร

### ปรับโฟลว์สมุดและ PetID — 12 ตุลาคม 2026

- **สแกนสมุดสุขภาพเป็นชุด:** ถ่ายเพิ่มทีละหน้า หรือเลือกรูปหลายหน้า รวมได้ 1–10 หน้า ดูตัวอย่าง ลบและเรียงลำดับได้ก่อนกดประมวลผลครั้งเดียว รูปยังไม่ถูกส่งอ่านด้วย AI ระหว่างสะสมหน้า ผลอ่านระบุหน้าต้นทาง และมีคำอธิบายรวมเป็น bullet points ในกล่องเดียว ตรวจ/แก้วันและรายการก่อนยืนยันบันทึก การส่งซ้ำหลังการเชื่อมต่อขัดข้องไม่สร้างรายการซ้ำ
- **สมุดประจำตัวอ่านง่ายขึ้น:** โปรไฟล์น้อง น้ำหนักล่าสุด วันนัดถัดไป และไทม์ไลน์แยกเป็นส่วนที่มีลำดับชัดเจน แบบตรวจผลสแกนแสดงรูปหน้าต้นทางคู่กับรายการที่แก้ไขได้
- **สมุดความทรงจำ:** เริ่มที่หน้าปกซึ่งแต่งเองหรือสั่ง AI ได้ เปิดอ่านทีละหน้า มีแถบความคืบหน้า/ก่อนหน้า/ถัดไป เพิ่ม แก้ และลบหน้าแยกกัน สมุดเริ่มมีหน้าเดียวได้และเก็บถาวร ไม่หมดอายุใน 24 ชั่วโมง สมุดส่วนตัวแยกตามผู้เขียนและน้อง แม้ผู้เขียนมีสิทธิ์ดูแลน้องร่วมกัน
- **แต่งหน้าแบบ Story:** หน้าใหม่เป็นแนวตั้ง 9:16 เพิ่มรูป ข้อความ สติกเกอร์ วันที่ และสถานที่ ลากย้าย แตะเลือก ย่อ/ขยายด้วยปุ่ม แถบเลื่อน จับมุม หรือใช้สองนิ้ว และหมุนได้ ไม่มีช่องขนาดรูปเป็นตัวเลข หน้าเดิม 800×1000 ยังคงเนื้อหาและตำแหน่งเดิมไว้ ภาษาในส่วนควบคุมสลับได้โดยไม่เปลี่ยนข้อความที่ผู้ใช้เขียน
- **PetID หลายมุม:** อัปโหลดหรือถ่าย 1–5 รูป จากนั้นกดให้ AI ร่างจุดสังเกตเอง ผู้ใช้แก้ข้อความ ตรวจรูป และยืนยันก่อนลงทะเบียน ลำดับ/จำนวนรูปที่เปลี่ยนต้องสร้างร่างใหม่ ระบบเก็บหนึ่งเวกเตอร์จากข้อมูลภาพหลายมุม แล้วตรวจคู่ภาพด้วย LLM เพื่อคัดตัวที่อาจคล้ายกัน เจ้าของยังต้องยืนยันผล เมื่อรูปอ้างอิงถูกลบ ระบบล้าง signature/embedding ที่เคยสร้างจากชุดรูปนั้น
- **เข้าจาก LIFF:** เริ่ม LIFF SDK แลก token ที่ตรวจฝั่ง server แล้วเปิดหน้าหลักอัตโนมัติ ผู้ใช้ที่ยังไม่อนุญาต service consent ยังต้องเลือกยินยอมด้วยตนเอง เบราว์เซอร์ปกติยังมีทางเลือกเข้าสู่ระบบและพื้นที่ตัวอย่าง การออกจากระบบยกเลิกผลการเข้าสู่ระบบที่ยังรออยู่

ฟีเจอร์นี้ใช้ migration `202610110015_memory_books_petid_photos.sql` ฐานข้อมูลเดิมให้ใช้ `supabase/upgrade.sql` ซึ่งตรวจสถานะและเพิ่มเฉพาะ migration ที่ขาด ห้ามรัน bootstrap ซ้ำ

## Key feature ที่ดึงผู้ใช้ใหม่

1. **ถ่ายสมุดวัคซีน → ตรวจร่าง → บันทึก → มีวันเตือน** เป็นคุณค่าแรกที่อธิบายง่ายและแก้ปัญหาของเจ้าของทันที ความไม่ชัดเจนต้องให้เจ้าของตรวจและยืนยัน
2. **สมุดน้องที่ตกแต่งได้** ทำให้การดูแลสุขภาพมีความรู้สึกส่วนตัว ผู้ใช้ลากรูปและสติกเกอร์เอง หรือพิมพ์ว่า “ทำธีมพาสเทลและจัดรูปไว้ด้านซ้าย” แล้วดูร่างก่อนบันทึก
3. **เช็กความเร่งด่วนและข้อมูลฉุกเฉิน** ให้ประโยชน์เวลาผู้ใช้กังวล กฎฉุกเฉินต้องทำงานแม้ AI ใช้ไม่ได้ เป็นการคัดกรองความเร่งด่วน ไม่ใช่การวินิจฉัยหรือสั่งยา
4. **ประกาศน้องหายและสรุปแชร์ก่อนพบหมอ** สร้างทางให้คนภายนอกเข้าถึงคุณค่าของระบบผ่านลิงก์ และกลับมาเริ่มใช้งานเมื่อมีน้องของตัวเอง

PetID เป็นฟีเจอร์ดึงดูดที่ต้องสื่อสารอย่างแม่นยำ: รูปคล้ายกันเป็นเพียง candidate เจ้าของต้องยืนยันทุกครั้ง ยังไม่ใช่หลักฐานยืนยันตัวหรือระบบแทนไมโครชิป

## ฟีเจอร์ที่ทำให้ผู้ใช้อยู่ต่อ

| กลไก | ฟีเจอร์หลัก | เหตุผลที่จะกลับมา |
|---|---|---|
| มีงานดูแลตามกำหนด | เตือนวัคซีน/ยา/ป้องกันปรสิต, ปฏิทิน, เลื่อน/ทำแล้ว | กลับมาเมื่อมีเรื่องที่ควรทำ ไม่ต้องพึ่งการเปิดแอปทุกวัน |
| ข้อมูลสะสมมีคุณค่า | ไทม์ไลน์, น้ำหนัก, บันทึกสุขภาพ, สรุปให้หมอ | ยิ่งบันทึกยิ่งเห็นประวัติและพร้อมใช้งานเมื่อเข้าคลินิก |
| ความผูกพันกับน้อง | สมุดตกแต่งเอง, รูปและเรื่องราว | มีเหตุผลกลับมาบันทึกช่วงเวลาดี ๆ ควบคู่การดูแล |
| ความคุ้นเคยกับผู้ช่วย | บุคลิก, บทสนทนาต่อเนื่อง, memory ที่ผู้ใช้ควบคุม | คุยต่อได้สะดวกและได้คำตอบที่เหมาะกับบริบท |
| ทุกคนดูแลร่วมกัน | carer/viewer, ประวัติระบุผู้บันทึก | สมุดเป็นข้อมูลร่วมของครอบครัว |
| วงจรบ้าน–คลินิก | ขอเข้าพบ, ให้สิทธิ์สรุป, เตือนรอบถัดไป | ข้อมูลใช้ได้ทั้งก่อนและหลังพบหมอ |

เป้าหมาย activation ใน 7 วัน, retention เดือนที่ 2, ความตรงกับหมอ และงบในเอกสารเป็น **เป้าที่ต้องวัดจริง** ยังไม่มีตัวเลขที่ยืนยันว่า pilot ทำได้แล้ว

ประวัติสุขภาพเป็นข้อมูลของน้อง เมื่อผู้ดูแลร่วมลบบัญชี ประวัติที่เคยบันทึกให้น้องของเจ้าของคนอื่นยังอยู่ต่อ โดยลบข้อมูลอ้างอิงผู้บันทึกออก การลบน้องหรือบัญชีเจ้าของน้องจึงค่อยลบประวัติของน้องนั้น

## สมุดตกแต่งสองวิธี

**วิธีที่ 1: ทำเอง** เพิ่ม/เลือกองค์ประกอบ ย้ายตำแหน่ง ปรับสีและข้อความแล้วบันทึกเป็น JSON ของหน้า สมุดแยกจากระเบียนสุขภาพ การย้ายสติกเกอร์จึงไม่เปลี่ยนวันนัดหรือผลคัดกรอง มีเลข `version` เพื่อตรวจการบันทึกทับหน้าเมื่อมีหลายแท็บ

**วิธีที่ 2: สั่ง AI** ส่งคำบอกธีมและโครงหน้าปัจจุบันให้โมเดล คืนร่างที่ผ่าน schema validation เป็นสี/ข้อความ/ตำแหน่ง/สติกเกอร์ที่อนุญาต ผู้ใช้ตรวจร่างและบันทึก ไม่รัน HTML, JavaScript หรือคำสั่งฐานข้อมูลที่โมเดลสร้าง

งาน AI นี้ใช้ config เดียวกับ OCR, chat, triage และ vision ค่าเริ่มต้นคือ `gpt-6.1-sol` หากบัญชี API ไม่รองรับชื่อนี้ต้องแจ้งข้อผิดพลาดชัดเจน ไม่มีการเปลี่ยนไปใช้ LLM เดิมเงียบ ๆ งาน embedding ของ PetID ใช้ `text-embedding-3-small` ซึ่งเป็น API สำหรับเวกเตอร์โดยเฉพาะและแยก config จาก LLM

## Chat และ memory

- เรียก OpenAI API ผ่าน client กลาง ใช้ประวัติจากฐานข้อมูลส่งกลับเป็นบริบทให้โมเดล การตอบต่อเนื่องไม่พึ่ง state ใน process ของ Vercel
- Personality มาจากชื่อผู้ช่วย โทน และคำอธิบายที่ผู้ใช้เลือก ไม่ใช่การปลอมตัวเป็นผู้เชี่ยวชาญหรือเก็บข้อมูลลับ
- Memory แยกจากข้อความสนทนา ผู้ใช้ต้องเปิดใช้เอง และสามารถดู/เพิ่ม/ลบแต่ละรายการหรือปิดทั้งหมด การถอนความยินยอมปิดการใช้ memory ทันที
- ข้อมูลส่วนตัวของผู้ใช้แต่ละคนแยกด้วย RLS ผู้ดูแลร่วมของน้องไม่เห็นแชตหรือ memory ของเจ้าของโดยอัตโนมัติ
- ถ้าปิด memory ประวัติบทสนทนาภายในห้องยังใช้คุยต่อได้ ความจำข้ามห้องจะไม่ถูกนำมาใช้

## เทียบกับข้อกำหนดทั้ง 32 ข้อ

“มี flow” หมายถึงมีโค้ดใช้งานกับฐานข้อมูล/API จริง แต่ยังต้องใส่ env และทดสอบกับบัญชีจริง “บางส่วน” หมายถึงทำแล้วเฉพาะส่วนที่ระบุ ไม่ได้ยืนยันเกณฑ์ทั้งหมดในเอกสารต้นฉบับ

| Requirement | สถานะโค้ด pilot | ส่วนที่ยังต้องทำ/พิสูจน์ |
|---|---|---|
| FR-01 LINE login | มี flow server verify token | ทดสอบ consent screen/จำนวนแตะบน LINE จริง |
| FR-02 consent | มี state+history+ถอน | ตรวจข้อความประกาศและ version ทางกฎหมาย |
| FR-03 export/delete | มี JSON export และ cascade+Blob deletion job | export รูปเป็น ZIP, backup retention, DSR จบจริง≤24ชม. |

## Architecture ที่ใช้งานรุ่นนี้

สร้าง **1 Git repository** แล้วเชื่อม **4 Vercel projects**: owner-app, clinic-portal, admin-console และ backend ภายใน backend แยก13บริการเชิงธุรกิจ (11เดิม+ journal+ assistant) และ scheduler งาน retry ใช้คิวทนทานใน PostgreSQL ในรุ่นนี้

Git repository, Vercel project และ service เป็นคนละสิ่ง ไม่ต้องสร้าง repoต่อmicroservice ภายใน pilot แต่ละserviceมีschemaของตัวเองแต่ใช้ roleแอปร่วมกัน การdeployร่วมและFKข้ามschemaช่วยให้คนเดียวดูแลง่ายและลบบัญชีครบ หากต้องการบริการdeployอิสระหรือแยกฐานข้อมูลจริง ต้องทำrole/service contract และevent cleanupเพิ่มตามสถาปัตยกรรมตั้งต้น

เอกสารเดิมมี162API/43topicและแผน16สัปดาห์ โค้ดนี้เป็นpilotที่มีflowหลักใช้งานได้ ไม่ได้อ้างว่างานครบทุกacceptanceในแผนดังกล่าว Testที่ผ่านด้านRLS/queueไม่แทนclinical eval100เคส, reviewจากสัตวแพทย์, load/security test, การซ้อมrestore หรือ legal reviewของPDPA
