# LINE Agent — สั่งให้ชิดใจทำงานผ่านแชท

เอกสารนี้อธิบายพฤติกรรมที่พัฒนาในโค้ด วิธีเปิดใช้งาน และขอบเขตของ Agent ใน LINE OA ของชิดใจ สำหรับผู้ดูแลระบบ นักพัฒนา และทีม Product อ่านคู่กับ [FEATURES.md](FEATURES.md), [PERSONALIZED_FOLLOWUPS.md](PERSONALIZED_FOLLOWUPS.md), [PET_PASSPORT.md](PET_PASSPORT.md) และ [VERIFICATION.md](VERIFICATION.md)

**สถานะล่าสุด:** ผู้ดูแลรัน SQL และตั้ง env จริงเองแล้ว ฐานข้อมูลจริงที่ตรวจแบบ read-only เป็นรุ่น 23 ฟีเจอร์แก้/ลบบันทึกใช้รุ่น 23 เพิ่มจาก LINE Agent รุ่น 22 ไม่มี env ใหม่ ผู้ใช้เลือกทดสอบข้อความจริงกับพีโอนีเอง ผล deploy/fixtures และสิ่งที่ยังไม่ยืนยันในบัญชีจริงอ่านใน [VERIFICATION.md](VERIFICATION.md) และ [RECORD_MUTATIONS.md](RECORD_MUTATIONS.md) ค่าเริ่มต้นใน env example ยังปิด `LINE_AGENT_ENABLED` เพื่อไม่เปิดบริการอัตโนมัติใน environment ใหม่

ผลตรวจข้อความจริงและการแก้ Chat guard, ข้อความรับแล้ว, loading animation, อ่านแล้ว และ stage logs อยู่ใน [LINE_AGENT_FEEDBACK.md](LINE_AGENT_FEEDBACK.md) การเล่าแผนไปพบหมออย่างเดียวยังเป็น Chat ต้องขอบันทึกก่อนสร้างไดอารี่

## 1. เป้าหมายของประสบการณ์ใช้งาน

เจ้าของเล่าเรื่องของน้องใน LINE ที่ใช้อยู่แล้ว และสั่งให้ชิดใจเก็บข้อมูลหรือทำรายการให้ได้ เช่น

> วันนี้พาน้องถั่วเหลืองไปหยอดหลังคอกำจัดไรหูมา บันทึกไว้ให้หน่อยสิ

เมื่อรู้แล้วว่าถั่วเหลืองคือน้องตัวไหน ระบบสร้างบันทึกการพบหมอในไดอารี่ดูแลน้อง โดยเก็บสิ่งที่เจ้าของเล่าเป็นข้อมูลจากเจ้าของ และใช้วันที่ของข้อความเป็นจุดอ้างอิง ถ้าเจ้าของไม่ได้บอกชื่อยา คลินิก ราคา ขนาดยา หรือวันนัด ระบบไม่เติมข้อมูลเหล่านั้นเอง และไม่ต้องถามช่องที่เป็นข้อมูลเสริมทุกช่องก่อนบันทึก

ลำดับที่เจ้าของเห็นคือ

1. พิมพ์คำขอในแชทส่วนตัวกับ LINE OA
2. หากข้อมูลจำเป็นยังไม่ครบ จะได้รับการ์ดคำถาม กดคำตอบหรือพิมพ์คำตอบของตัวเองได้
3. งานที่ต้องตรวจยืนยันจะแสดงรายละเอียดและขอยืนยันก่อนทำ
4. เมื่อข้อมูลครบ จะได้รับข้อความว่า “ข้อมูลครบแล้ว กำลังทำงานให้คุณครับ”
5. เมื่อเสร็จ จะได้รับผลการทำงานและปุ่มเปิด LIFF ไปยังงานนั้น เช่น บันทึกไดอารี่ของถั่วเหลือง

การเข้า LIFF ยังมีประโยชน์สำหรับอ่านประวัติ ตรวจข้อมูลเต็ม อัปโหลดภาพ และทำรายการที่ต้องเลือกขอบเขตอย่างละเอียด ส่วนงานข้อความสั้นที่ชัดเจนทำผ่าน LINE ได้เลย

## 2. LLM0 แยกบทสนทนาจากคำสั่งอย่างไร

เส้นทางหลักในระบบคือ

```text
LINE OA ส่วนตัว
  → Webhook ตรวจลายเซ็น + เก็บ event + เข้าคิว
  → เริ่มงานเบื้องหลังทันทีบน Vercel; คิว/Cron รับช่วงหากทางด่วนทำไม่จบ
  → Worker ตรวจบัญชี สิทธิ์ ความยินยอม และ event ต้นฉบับ
  → ตรวจสัญญาณฉุกเฉินแบบกฎก่อนเรียก LLM
  → LLM0: classify + normalize
      ├─ chat             → AI Chat เดิม + ประวัติบทสนทนา
      ├─ followup_reply   → เก็บคำตอบ check-in แบบส่วนตัว หรือส่งต่อ Chat
      ├─ agent            → อ่านข้อมูลที่จำเป็น → ถามเพิ่ม/ขอยืนยัน → ทำงานด้วย tools
      ├─ help             → บอกความสามารถและเปิดแอป
      ├─ emergency        → แนะนำติดต่อสัตวแพทย์ทันที
      └─ unsupported      → อธิบายขอบเขตที่ทำได้
  → Outbox เก็บข้อความตอบ → LINE Push → LIFF เปิดผลด้วยสิทธิ์ปัจจุบัน
```

LLM0 คืนผลแบบมี schema ได้แก่ `route`, `language`, `normalizedText`, `intentSummary` และ `petMentions` การ normalize ต้องรักษาชื่อ วันเวลา จำนวนเงิน คำปฏิเสธ และความไม่แน่ใจตามต้นฉบับ ไม่แปลงการคุยทั่วไปให้เป็นคำสั่งบันทึกเอง

| ข้อความตัวอย่าง | พฤติกรรมที่ตั้งใจ |
| --- | --- |
| “แมวเกาหูเกิดจากอะไรได้บ้าง” | คุยกับ AI Chat ไม่สร้างไดอารี่ |
| “วันนี้ถั่วเหลืองเกาหู บันทึกให้หน่อย” | วางแผนสร้างบันทึกอาการ |
| “How do I record a diary for ถั่วเหลือง?” | อธิบายวิธีใช้; หาก LLM0 จัดเส้นทางผิด กฎฝั่งเซิร์ฟเวอร์ยังไม่ให้เขียนโดยไม่มีการตรวจยืนยัน |
| “บันทึกให้น้องหน่อย” แต่มีน้องหลายตัว | ถามว่าจะบันทึกให้น้องตัวไหน |
| “ตั้งเตือนพาถั่วเหลืองไปหาหมอ” | ถามวันและเวลาที่จำเป็นก่อนตั้งเตือน |
| “ดีขึ้นแล้วครับ” ในการติดตามอาการ | เก็บคำตอบ check-in แบบส่วนตัวตามบริบท ไม่ตีความเป็นการยืนยันว่าหายหรือสร้างเวชระเบียนเอง |
| รายงานอาการชักหรืออาการฉุกเฉินที่ตรวจพบ | ส่งทางไปขอความช่วยเหลือทันที ไม่รอให้กรอกงานให้ครบ |

การจัดเส้นทางของ LLM ไม่ใช่สิทธิ์ทำรายการ เซิร์ฟเวอร์ตรวจประเภท tool, schema, บัญชี, สิทธิ์ในน้อง และการยืนยันอีกชั้นเสมอ

## 3. การถามต่อและการยืนยัน

### คำถามที่ตอบได้ทั้งปุ่มและข้อความ

Planner อ่านข้อมูลที่เจ้าของมีสิทธิ์เพื่อระบุสิ่งที่ขาด แล้วถามครั้งละคำถามที่เกี่ยวข้อง เช่น เลือกน้อง ระบุวันเวลา หรือเลือกว่าหมายถึงรายการใด การ์ดรองรับตัวเลือกสูงสุด 8 ปุ่มและบอกชัดว่าพิมพ์คำตอบเองได้

ปุ่มส่ง `postback` ที่อ้างถึงตัวเลือกในฐานข้อมูล ไม่ส่งแผนงานหรือสิทธิ์จากฝั่งผู้ใช้ ตัวเลือกผูกกับเจ้าของ งาน รุ่นของงาน และเวลาหมดอายุ ใช้ได้ครั้งเดียว ปุ่มเก่า ปุ่มของคนอื่น หรือปุ่มที่ข้อมูลเปลี่ยนแล้วใช้ยืนยันงานใหม่ไม่ได้

หากระบุชื่อน้องไม่ตรงกับข้อมูล น้องหลายตัวมีโอกาสตรงกัน หรือโมเดลเลือก ID ของน้องผิด แม้เป็นน้องอีกตัวในบ้านเดียวกัน เซิร์ฟเวอร์จะหยุดให้เลือก ไม่เลือกตัวแรกในรายชื่อเป็นค่าเริ่มต้น

### งานที่ต้องตรวจยืนยันก่อนทำ

Tools แบ่งเป็น 3 ระดับ

- `read`: อ่านข้อมูลที่มีสิทธิ์ ไม่แก้ข้อมูล
- `write`: สร้างข้อมูลจากคำสั่งชัดเจน เช่น “บันทึกให้หน่อย” หรือ “ตั้งเตือนวันที่…” หากเจตนาเขียนไม่ชัด ต้องตรวจยืนยันก่อน
- `confirm`: แก้ข้อมูลเดิม ลบความจำ เพิกถอนลิงก์ ส่งคำขอนัดหมาย หรือเผยแพร่ประกาศ ต้องมีการยืนยันแยกก่อนเสมอ

การ์ดยืนยันแสดงชื่อ tool และค่าที่จะทำรายการ หากรายละเอียดเกินพื้นที่ที่ตรวจได้บนการ์ด ระบบให้เปิดแอปเพื่อตรวจข้อมูลเต็ม ไม่ตัดส่วนสำคัญแล้วให้กดยืนยัน

การยืนยันอ้างถึง `version` ของแผนปัจจุบัน โมเดลยืนยันแทนเจ้าของไม่ได้ เจ้าของกดปุ่ม หรือพิมพ์คำยืนยันที่รองรับ เช่น “ยืนยัน”, “ตกลง”, “ทำเลย”, “confirm”, “yes” ได้ เฉพาะเมื่อมีงานรอยืนยันอยู่ ข้อความยืนยันที่ webhook รับไว้ก่อนออกการ์ดยืนยันรุ่นปัจจุบันไม่สามารถนำมายืนยันการ์ดใหม่ย้อนหลังได้

### วันเวลาและการถามต่อข้ามวัน

งานมี `reference_at` ที่เก็บเวลารับ webhook ของคำขอต้นฉบับและเปลี่ยนไม่ได้ Planner ได้ทั้ง `requestTime` ของคำขอเดิมและ `currentReplyTime` ของคำตอบล่าสุด คำว่า “วันนี้/เมื่อวาน” จึงอ้างอิงข้อความนั้นในเขตเวลา `Asia/Bangkok` ไม่เลื่อนตามเวลาที่ worker หยิบงานมาทำหลังเที่ยงคืน ปี พ.ศ. และ ค.ศ. ต้องแยกให้ถูก หากวันเวลายังตีความได้หลายแบบต้องถามเพิ่ม

## 4. Tools ที่เปิดให้ Agent ใช้

รุ่นนี้มี **55 tools: อ่าน 23, สร้าง 10, ต้องยืนยัน 22** ใช้ API และตัวตรวจสิทธิ์จริงของบริการเดิมผ่านรายการที่กำหนดไว้ล่วงหน้า โมเดลเลือก host, SQL, โค้ด, HTTP method หรือผู้รับ LINE เองไม่ได้ จำนวนและรายละเอียดล่าสุดตรวจได้จาก `GET /api/v1/assistant/agent/tools` เมื่อเข้าสู่ระบบ

บันทึกค่าใช้จ่ายใช้หน่วยย่อยของสกุลเงิน เช่น 550 บาทเป็น `amountMinor=55000` ถ้าเจ้าของไม่ทราบราคาให้เป็นไม่ทราบ ไม่บันทึกเป็นศูนย์ รูปแบบที่บันทึกยังแยกสิ่งที่เจ้าของรายงานออกจากข้อมูลที่คลินิกเป็นผู้ยืนยัน

Planner จำกัดไม่เกิน 3 รอบต่อการวางแผนหนึ่งครั้ง และไม่เกิน 4 actions ต่อแผน Actions ในแผนต้องทำได้อย่างอิสระ หากขั้นตอนถัดไปต้องใช้ ID จากการสร้างข้อมูลในขั้นแรก ให้ทำเป็นงานถัดไป ไม่ใช้ตัวแทน ID ที่ยังไม่มีจริง

## 5. งานที่เจ้าของต้องทำใน LIFF

การมี Agent ไม่ได้ย้ายการให้สิทธิ์หรือการยินยอมมาเป็นการคาดเดาจากบทสนทนา จุดเหล่านี้ยังมีหน้าตรวจโดยเจ้าของ

| งาน | หน้าที่เปิด | เหตุผล |
| --- | --- | --- |
| ให้/เปลี่ยนสิทธิ์คลินิก ผู้ดูแล และขอบเขตแชร์ | ตั้งค่าและหน้าสิทธิ์ที่เกี่ยวข้อง | เจ้าของต้องเห็นว่ากำลังให้ใครอ่านหรือเขียนข้อมูลส่วนใด |
| เปิด memory หรือ optional LINE follow-up และเลือกแหล่งข้อมูล | `/app?tab=settings` | เป็นความยินยอมแยกจากการคุยหรือสั่งบันทึก |
| ลบบัญชี/จัดการคำขอความเป็นส่วนตัว | `/app?tab=settings` | ต้องเห็นผลกระทบต่อข้อมูลก่อนดำเนินการ |
| ถ่ายภาพ PetID หลายมุม ยืนยันว่าเป็นตัวเดิม และยินยอมฝึกโมเดล | `/app?tab=care` | การยืนยันตัวตนและสิทธิ์วิจัยต้องมีหลักฐานและความยินยอมแยก |
| ตรวจอนุมัติชุดข้อมูล/การฝึก PetID | กระบวนการผู้ตรวจที่มีสิทธิ์ | ไม่เป็นเครื่องมือที่ผู้ช่วยของเจ้าของอนุมัติแทนได้ |
| ตรวจและยืนยัน Passport ฉบับสุดท้าย/สร้างลิงก์สาธารณะ | `/app?tab=health` | เจ้าของเห็นคำตอบ รูป และขอบเขตที่หมอหรือผู้รับจะเห็นครบก่อนแชร์ |
| อัปโหลด/ถ่ายรูปยา ใบเสร็จ สมุดสุขภาพ และภาพไดอารี่ | หน้าข้อมูลนั้นใน LIFF เช่น `/app?tab=health` | ใช้ขั้นตอนสื่อและสิทธิ์ที่ระบบรองรับ |
| ให้ AI จัดหน้าความทรงจำบน canvas และตรวจภาพก่อนบันทึก | `/app?tab=journal` | ต้องเห็นร่างทั้งหน้า รวมงานที่ยังไม่บันทึกก่อนรับการตกแต่ง |
| อ่าน/แก้ความรู้สึกส่วนตัวใน care reflection | ไดอารี่ใน LIFF | แยกพื้นที่ส่วนตัวออกจากข้อมูลที่ Agent อ่านและส่งเข้าโมเดล |

รุ่นนี้รับเข้า Agent จาก LINE เฉพาะ **ข้อความและ postback ในแชทส่วนตัว** ยังไม่ดึงภาพ เสียง วิดีโอ หรือไฟล์ที่ส่งมาในแชทไปวิเคราะห์/บันทึกอัตโนมัติ งานที่ต้องมีรูปให้เจ้าของเปิด LIFF อัปโหลดก่อน การมี tool ที่อ้างถึง media ID ไม่ได้หมายถึงรองรับไฟล์แนบจาก LINE แล้ว

## 6. งานถาวร การทำซ้ำ และผลสำเร็จบางส่วน

Agent ใช้คิวในฐานข้อมูลเดิมและแยกสถานะ `collecting → awaiting_confirmation → queued → running → succeeded/failed/cancelled` งานที่ไม่ต้องยืนยันข้าม `awaiting_confirmation` ได้ งานหนึ่งมีอายุเริ่มต้น 24 ชั่วโมง และหนึ่ง thread มีงานปัจจุบันทีละงาน

ก่อนแก้/ลบ server อ่านชื่อน้อง ชื่อรายการ และวันที่จากข้อมูลปัจจุบันมาประกอบการยืนยัน พร้อมระบุว่าลบถาวรไม่มีถังขยะ เก็บ prepared deletion receipt ที่เป็น reference ก่อนเรียก domain API เพื่อกู้ผลหลัง response หายโดยยังตรวจสิทธิ์และใช้ idempotency เดิม เมื่อข้อมูลเปลี่ยนจน version conflict ต้องส่งคำขอใหม่เพื่อตรวจฉบับล่าสุด ผลลบสำเร็จเปิดประวัติที่เหลือใน LIFF ไม่เปิดรายการที่ถูกลบแล้ว

ในหนึ่ง runtime instance มี process permit ให้ Agent ทำงานพร้อมกันหนึ่งงาน เพื่อเหลือ connection สำหรับการตรวจสิทธิ์และ domain API ที่เปิด transaction ซ้อน งานที่ชนกันคืน `409 AGENT_BUSY` ทันทีและคิวที่บันทึกไว้จะลองใหม่ จึงอาจรอรอบถัดไปได้ permit ถูกคืนแม้งานผิดพลาด ส่วนการป้องกันข้าม instance ยังคงใช้ lock, execution lease และ idempotency ในฐานข้อมูล ไม่พึ่งตัวแปรใน process เพียงอย่างเดียว

ตารางใหม่อยู่ใน schema `assistant`

| ตาราง | เก็บอะไร |
| --- | --- |
| `agent_threads` | บริบทเจ้าของ ภาษา งานปัจจุบัน และการเชื่อมบทสนทนา Chat เดิม |
| `agent_turns` | event ข้อความ/ปุ่ม ผล normalize เส้นทาง และ request ID ที่คงเดิมเมื่อ retry |
| `agent_tasks` | คำขอ เวลาอ้างอิง แผน รุ่น การยืนยัน สถานะและผลอ้างอิง |
| `agent_tool_calls` | tool/arguments/key ของแต่ละขั้นตอน พร้อมสถานะและ receipt |
| `agent_deliveries` | ข้อความตอบใน outbox, dedupe key, LINE retry key และเวลาหมดอายุ |
| `agent_choices` | ตัวเลือกปุ่มที่ผูกบัญชี/งาน/รุ่น/วันหมดอายุ |

เมื่อ webhook หรือ worker ส่งซ้ำ ระบบใช้ event ID, task step และ idempotency key เดิม ไม่วางแผนหรือสร้างไดอารี่ใหม่ทุกครั้ง ในขั้น execute การเรียก domain API ไม่ถูกครอบด้วย transaction ใหญ่ของ Agent หาก domain บันทึกสำเร็จแล้วแต่การตอบกลับหาย การลองใหม่ใช้ key เดิมเพื่อขอผลเดิม

Receipt ที่สำเร็จเก็บการอ้างอิง เช่น tool, path, resource ID และ pet ID ไม่เก็บสำเนาเวชระเบียนเต็มในผล tool หน้าผล LIFF อ่าน resource จริงอีกครั้งด้วยสิทธิ์ปัจจุบัน

หากงานมี 2 ขั้นตอนและทำสำเร็จเพียงขั้นแรก ระบบแจ้งจำนวนขั้นตอนที่สำเร็จและให้กดลองส่วนที่ค้าง เมื่อ retry จะรักษา key และข้ามขั้นตอนที่มี receipt สำเร็จแล้ว ผลของการทำงานข้ามบริการไม่ใช่ transaction เดียวที่ย้อนคืนทั้งหมดได้ หากไม่แน่ใจว่ารายการใดสำเร็จ ให้ตรวจหน้าผลก่อนสั่งสร้างรายการใหม่

เจ้าของพิมพ์ “ยกเลิก”, “หยุดงาน”, “cancel” หรือใช้ปุ่มยกเลิกได้ ระบบหยุดส่วนที่ยังไม่เริ่ม งานที่บันทึกไปแล้วหรือคำขอที่ส่งออกไปขณะกำลังยกเลิกอาจยังสำเร็จได้ ต้องเปิดตรวจผลในแอป การยกเลิกไม่ลบประวัติหรือยกเลิกนัดหมายย้อนหลังแทนเจ้าของ

## 7. บทสนทนาต่อเนื่อง ความจำ และ LINE follow-up

เส้นทาง `chat` ใช้บริการ AI Chat เดิม และ conversation/request ID ที่คงเดิมต่อบัญชี LINE เพื่อให้ตอบต่อจากประวัติได้ ไม่สร้างห้องคุยใหม่ทุกข้อความ บริบทที่ส่งเข้าโมเดลจำกัดขนาด ประวัติ Chat กับ memory ระยะยาวเป็นคนละส่วน

- ประวัติ Chat ช่วยตอบต่อจากบทสนทนาเดิม
- optional memory ช่วยเรื่องชื่อผู้ช่วย บุคลิก ความชอบ และข้อเท็จจริงที่เจ้าของอนุญาตให้จำ ต้องเปิดทั้ง preference และความยินยอม `ai_memory`
- การเก็บคำตอบ follow-up เป็นข้อมูลตอบกลับส่วนตัว ไม่ใช่คำสั่งให้เปลี่ยนสถานะโรค ลงยา หรือสร้างไดอารี่ หากเจ้าของต้องการบันทึกให้พิมพ์คำสั่งชัดเจน
- optional follow-up เชิงรุกยังใช้กติกาความถี่ ช่วงเวลาที่ส่ง ความยินยอม แหล่งข้อมูล และคำสั่งพัก/กลับมารับข้อความเดิม ดู [PERSONALIZED_FOLLOWUPS.md](PERSONALIZED_FOLLOWUPS.md)

ข้อความตอบงานที่เจ้าของเพิ่งสั่งเป็นอีกประเภทหนึ่งจากข้อความ follow-up เชิงรุก การพัก optional follow-up ไม่ได้แปลว่าระบบเลิกตอบคำขอที่เจ้าของส่งมาด้วยตนเอง

## 8. ความเป็นส่วนตัวและสิทธิ์

ผู้รับ LINE ถูกระบุจาก `line_user_id` ที่ผูกกับบัญชีและ event ที่ตรวจแล้ว โมเดลส่ง user ID หรือเลือกคนอื่นเป็นผู้รับไม่ได้ ไม่รับงานจาก group/room และตรวจซ้ำว่า event ต้นฉบับเป็นข้อความของบัญชีที่กำลังดำเนินงาน พร้อมกรอบความสดของ event ไม่เกิน 24 ชั่วโมง ผู้ใช้ใหม่ต้องเข้า LIFF เพื่อเข้าสู่บัญชีและตรวจ service consent ก่อน Agent จึงทำงานกับข้อมูลส่วนตัวได้

ก่อนวางแผน ก่อนแต่ละ tool ก่อนอ่านผล และก่อนส่งข้อความ ตรวจสถานะบัญชี ความยินยอมใช้บริการ และสิทธิ์ที่เกี่ยวข้องอีกครั้ง ผลที่เก็บเป็น reference มี pet IDs สำหรับตรวจสิทธิ์ใหม่ รวมกรณีอ่านรายชื่อหลายตัว หากเจ้าของเสียสิทธิ์ในข้อมูล ระบบปิดรายละเอียดของผล/คำถามที่อาจเปิดเผยข้อมูลและไม่ส่งข้อความที่ค้างซึ่งใช้สิทธิ์เดิม ผลอ่านมี digest สำหรับเทียบข้อมูลปัจจุบันก่อนส่งสรุปที่ค้างอยู่ หากรายการถูกลบ/เปลี่ยนหรือถอนความยินยอม memory จะไม่ส่งคำตอบเดิมโดยอ้างเพียงว่ายังมีสิทธิ์ในน้องตัวนั้น

RLS ของตาราง Agent ให้แอปอ่านข้อมูลของเจ้าของเท่านั้น ไม่ให้ผู้ใช้แก้ plan, tool arguments, results หรือ confirmation ผ่าน SQL/API ตรง ตัวเลือกปุ่มเป็นข้อมูล worker ส่วนตัว ผู้ดูแลระบบไม่ได้สิทธิ์อ่านประวัติของทุกบัญชีเพียงเพราะมี role admin

เมื่อถอน service consent หรือบัญชีถูกระงับ trigger จะยกเลิกงานที่ยังไม่จบ ใช้ตัวเลือกเดิมต่อไม่ได้ และล้างข้อความตอบที่ยังไม่ส่ง การยินยอมใหม่ไม่ฟื้นงานเก่าอัตโนมัติ คำขอที่ส่งถึงบริการก่อนถอนสิทธิ์ไปแล้วอาจทำสำเร็จ จึงยังต้องตรวจผลจริงเมื่อเกิดเหตุพร้อมกัน

ข้อมูลที่ส่งให้ planner ถูกตัดขนาดและกรองความรู้สึกส่วนตัว, token และ temporary image URL ออกจากผลอ่าน กติกานี้ไม่ทำให้ข้อความต้นฉบับที่ผู้ใช้พิมพ์ปลอดข้อมูลอ่อนไหว หากเจ้าของพิมพ์รายละเอียดสุขภาพมาเอง รายละเอียดที่จำเป็นยังเป็นส่วนหนึ่งของการประมวลผลตามงานนั้น

### ระยะเวลาเก็บข้อมูล

- Raw Agent turns และ tasks เข้าการล้างเมื่อเก่ากว่า **30 วัน** ผ่าน Cron แบบทยอยลบ รายการย่อยของงาน/turn ลบตามความสัมพันธ์ จึงไม่ใช่การลบตรงวินาทีที่ครบกำหนด
- ตัวเลือกหมดอายุและ outbox หมดอายุถูกเก็บกวาดโดย scheduler; payload webhook ถูกล้างเมื่อประมวลผล turn เสร็จ และมี retention webhook เดิม 7 วัน
- การลบ task หลัง 30 วันไม่ลบไดอารี่ สมุดสุขภาพ หรือนัดหมายที่เจ้าของตั้งใจบันทึกไว้ ลิงก์หน้าผลงาน Agent เดิมอาจเปิดไม่ได้แล้ว แต่ยังอ่านรายการที่บันทึกจากเมนูปกติได้
- ข้อความที่ถูกส่งต่อเข้า **AI Chat เดิม** เป็นประวัติ Chat และยังอยู่จนเจ้าของลบบทสนทนาหรือบัญชี ไม่อยู่ภายใต้การลบ raw Agent 30 วัน ความจำที่เจ้าของสั่งบันทึกก็มีวงจรจัดการของตัวเอง
- การส่งออกข้อมูลเจ้าของรวม input ที่เจ้าของส่ง, metadata ของงาน และ receipt อ้างอิงที่ยังเก็บอยู่ ไม่ replay title/question/plan/request text ที่คัดลอกจากข้อมูลเดิม หรือ tool arguments ผ่าน historical task export และไม่ส่งค่า choice token/LINE retry key รายการงานทั่วไปก็ใช้ชื่อกลางและไม่ส่งรายละเอียดเหล่านี้ การลบบัญชีใช้การลบตามความสัมพันธ์ของเจ้าของ
- ข้อความที่ส่งถึง LINE ไปแล้วไม่ถูกดึงกลับจากแชทด้วยการลบแถวในฐานข้อมูล

| `GET /api/v1/assistant/agent/tools` | อ่านความสามารถและสถานะ flag | App session |
| `GET /api/v1/assistant/agent/tasks` | รายการงานล่าสุดของเจ้าของ มี metadata; ไม่ส่งรายละเอียดคำถาม/ผลเต็มในรายการ | App session + RLS |
| `GET /api/v1/assistant/agent/tasks/:id` | เปิดผลของงานหนึ่งรายการ | App session + เจ้าของงาน + ตรวจสิทธิ์ปัจจุบัน |

API ฝั่งแอปใช้ API origin/rewrite เดิม การทราบ task UUID ไม่ใช่สิทธิ์อ่านงาน

### Endpoint ภายในสำหรับ worker

| Method / Path | Body / หน้าที่ |
| --- | --- |
| `POST /internal/agent/ingest` | `{ "eventId": "...", "userId": "UUID" }` โหลด event ที่ตรวจแล้วจากฐานข้อมูล ไม่รับข้อความปลอมแทนต้นฉบับ |
| `POST /internal/agent/execute` | `{ "taskId": "UUID" }` ทำขั้นตอนของแผนที่พร้อมแล้ว |
| `POST /internal/agent/deliver` | `{ "deliveryId": "UUID" }` ส่งข้อความจาก outbox ที่มีอยู่แล้ว |
| `POST /internal/agent/capture-followup` | `{ "userId": "UUID", "eventId": "...", "text": "..." }` ฝั่ง notification เก็บคำตอบ check-in ที่เกี่ยวข้อง |
| `GET /internal/cron/jobs` | scheduler เก็บกวาดและประมวลผลคิว |

ทุก internal endpoint ตรวจ `Authorization: Bearer <CRON_SECRET>` ด้วย secret เดิมที่ต้องยาวอย่างน้อย 32 ตัวอักษร ไม่ใส่ secret นี้ใน frontend ไม่ให้โมเดลเรียก endpoint โดยตรง และไม่ตั้งให้ลูกค้าเรียกส่งข้อความถึงผู้รับตามใจได้

คิวใช้ topic `agent.turn`, `agent.execute`, `agent.deliver` และบันทึกงานก่อนเริ่มประมวลผลเสมอ บน Vercel มีทางด่วนผ่าน `waitUntil`: หลัง webhook เก็บ event แล้ว เริ่มประมวลผล LINE เบื้องหลัง ส่งต่อไป private assistant binding และเร่ง execute/deliver งานที่พร้อม โดยไม่ต้องรอ Cron รอบแรก

ทางด่วนเป็น best effort และใช้เงื่อนไข `VERCEL` เดิม ไม่ต้องเพิ่ม flag ใหม่ หาก runtime ถูกหยุด บริการชั่วคราวไม่พร้อม หรือชนกับ worker อีกตัว คิวที่ commit ไว้ยังเป็นฐานสำหรับทำต่อ Cron `/internal/cron/jobs` ตั้งทุกนาที งานจึงอาจรอรอบถัดไปหรือช้ากว่านั้นเมื่อมี backlog ไม่รับประกันเวลาตอบทันทีหรือ streaming ให้ตรวจคิวและ quota หากความล่าช้าเพิ่มขึ้น

### LIFF ของผล Agent

ใช้ LIFF หลักเดิมได้ โดย endpoint ใน LINE Developers ยังคงเป็น

```text

```

ตัวอย่างลิงก์จากการ์ดที่เซิร์ฟเวอร์สร้าง

## 10. ข้อความ LINE และต้นทุน AI

ข้อความตอบของ Agent ในรุ่นนี้ส่งผ่าน **LINE Push API** จาก durable outbox ไม่พึ่ง reply token ที่อาจหมดอายุระหว่างรอคิว ทั้งการถามเพิ่ม รับทราบงาน และแจ้งผลจึงใช้โควตาข้อความของ OA ด้วย ต้องรวมต้นทุนนี้ในการออกแบบ onboarding และจำนวนรอบคำถาม

ข้อความที่ต้อง retry ใช้ LINE retry key เดิมและข้อความที่ persist ไว้ ไม่ให้ LLM เขียนใหม่ทุกครั้ง outbox มีอายุเริ่มต้น **23 ชั่วโมง** เพื่ออยู่ภายในหน้าต่าง retry key 24 ชั่วโมง เมื่อหมดอายุจะไม่ส่งด้วย key ใหม่เพื่อหลบกรอบนี้ การตอบสำเร็จจาก LINE หมายถึงระบบรับคำขอส่ง ไม่ได้ยืนยันว่าผู้ใช้อ่านแล้ว

LLM0, planner, สรุปคำตอบอ่านข้อมูล และ Chat ใช้ `gpt-6.1-sol` ผ่าน `packages/ai` ตัวเดียวกับระบบเดิม ไม่มีโมเดล Agent แยก การฝังเวกเตอร์ PetID ยังเป็นงาน embedding ของระบบเดิม ไม่ได้เปลี่ยนมาใช้ generative model สำหรับ embedding

Agent ใช้ Structured Outputs ผ่าน Responses API เพื่อคืนแผนที่ตรวจ schema แล้ว ให้ executor ฝั่งระบบเรียก tools ที่อนุญาต ไม่เปิดให้โมเดลรันโค้ดหรือเรียก HTTP/SQL เอง รุ่น prompt รอบนี้คือ `2026-10-29.3` และใช้ budget/usage log กลางของระบบเดิม แยกแผนอ่านออกจากแผนแก้ข้อมูล และแยกการวางแผนไปพบหมอจากการรักษาที่เกิดขึ้นแล้ว

เพดานที่ตั้งในโค้ดขณะส่งมอบ

| AI feature | เพดานต่อผู้ใช้/วันของระบบ AI | Timeout ต่อการเรียก |
| --- | --- | --- |
| `agent.normalize` | 80 ครั้ง | 15 วินาที |
| `agent.plan` | 120 ครั้ง | 25 วินาที |
| `agent.answer` | 80 ครั้ง | 15 วินาที |
| `assistant.chat` | 50 ครั้ง | 45 วินาที |

ตัวเลขเป็นจำนวนเรียก AI ไม่ใช่จำนวนงานที่ทำสำเร็จ หนึ่งงานอาจมี planner หลายรอบ มีงบรวมจาก `AI_DAILY_BUDGET_USD` ค่าเริ่มต้น 5 USD ต่อวันของระบบ และจองงบก่อนเรียก provider เพื่อป้องกัน instance หลายตัวใช้เกินพร้อมกัน วันตัดยอดอิง `date_trunc('day', now())` ของฐานข้อมูล ไม่ใช่ตัวกำหนดวันอาการใน Bangkok

`AI_INPUT_USD_PER_MILLION` และ `AI_OUTPUT_USD_PER_MILLION` ใช้ประเมินงบ ต้องตั้งตามราคาจริงของบัญชี ไม่ถือว่าค่าเริ่มต้นใน `.env.example` คือใบรับรองราคา provider หรือรับรองว่า project มีสิทธิ์ใช้โมเดลแล้ว ควรตรวจ provider access ใน smoke test ก่อนเปิดให้ผู้ใช้จริง

## 11. สิ่งที่ผู้ดูแลต้องทำก่อนเปิดใช้

### Supabase: อัปเกรดฐานข้อมูลเดิม

1. ใช้ SQL Editor ของ project จริงรัน [`supabase/diagnostic.sql`](../supabase/diagnostic.sql) เพื่ออ่านสถานะ ไม่มีการแก้ข้อมูล
2. หากเป็น ChordJai schema ที่สคริปต์รู้จัก ใช้ [`supabase/upgrade.sql`](../supabase/upgrade.sql) ฉบับที่มากับโค้ดรุ่นนี้ สคริปต์ตรวจ fingerprint/checksum ก่อนเพิ่ม migration ที่ขาด และทำใน transaction
3. รัน diagnostic อีกครั้ง ตรวจว่าถึง **รุ่น 23** และไม่มี partial/unknown schema แล้วจึงเปิด flag (โครงการนี้ผู้ดูแลรันและตรวจยืนยันแล้ว)
4. หากสคริปต์หยุดเพราะ schema ไม่ตรง ให้ตรวจผล diagnostic และความต่างก่อน ไม่ใช้การลบตารางหรือข้ามการตรวจเพื่อให้รันผ่าน

**ฐานข้อมูลนี้มีข้อมูลอยู่แล้ว ให้ใช้ `upgrade.sql` ไม่รัน `bootstrap.sql` ซ้ำ** การมี error ว่า relation `users` มีแล้วไม่ได้แก้ด้วยการลบตาราง เอกสาร [DEPLOYMENT.md](DEPLOYMENT.md) อธิบายขั้นตอนติดตั้งและ connection string เดิม

Agent ใช้ [`202610290022_line_agent.sql`](../supabase/migrations/202610290022_line_agent.sql) และการแก้/ลบที่ดูแลข้อมูลอ้างอิงใช้ [`202610290023_record_mutations.sql`](../supabase/migrations/202610290023_record_mutations.sql) ไม่ต้องเปิด schema `assistant` เป็น public Supabase REST schema บริการ backend ใช้ `DATABASE_URL` และ API เดิม ไม่มี env ใหม่สำหรับส่วนแก้/ลบ ดู [RECORD_MUTATIONS.md](RECORD_MUTATIONS.md)

### Environment ของ backend project

เพิ่มหรือกำหนดค่าใน **backend Vercel project** สำหรับ environment ที่จะใช้งาน แล้ว deploy ใหม่

```dotenv
LINE_AGENT_ENABLED=true
# Optional: หากไม่กำหนด จะใช้ LIFF_ID เดิม
LINE_AGENT_LIFF_ID=2010549060-FRfLt9mJ
```

เมื่อไม่มีค่า หรือไม่ใช่ตัวอักษร `true` ค่า flag ถือว่าปิดและ LINE ใช้พฤติกรรมเดิม จึงเตรียม deploy โดยปิดไว้ได้ก่อนอัปเกรดฐานข้อมูลเสร็จ

ใช้ค่าที่ตั้งอยู่แล้วให้ถูกต้อง ไม่ต้องสร้าง credential ชุดใหม่สำหรับ Agent

- `DATABASE_URL` ของฐานข้อมูลที่อัปเกรดแล้ว
- `OPENAI_API_KEY`, `OPENAI_MODEL=gpt-6.1-sol` และค่า AI budget/pricing ของระบบ
- `APP_JWT_SECRET`, `CRON_SECRET`, `APP_ORIGIN` และ API/origin เดิม
- LINE Messaging channel/token หรือการออก token ที่ระบบเดิมใช้ และ LINE Login/LIFF config เดิม

`ASSISTANT_INTERNAL_URL` ถูก inject ให้ notification/scheduler เรียก assistant และ `NOTIFICATION_INTERNAL_URL` ถูก inject ให้ scheduler เรียก notification ตาม `backend/vercel.json` ไม่ต้องกรอก URL public แทนเอง ส่วน assistant เก็บคำตอบ follow-up ผ่าน notification handler ภายใน process พร้อม worker auth เดิม จึงไม่ต้องมี binding ย้อนกลับและไม่เกิดวงจร `notification → assistant → notification` ซึ่ง Vercel ปฏิเสธ ฝั่ง local scheduler มี fallback ผ่าน dev API เดิม อย่าส่ง API key, channel secret หรือ connection string ที่มีรหัสผ่านในแชทหรือ commit ลง Git

ไม่ต้องเพิ่ม env ให้ owner/clinic/admin เพียงเพื่อเปิด Agent แต่ owner app ต้อง deploy โค้ดหน้าผลรุ่นใหม่ด้วยเพื่อเปิด deep link ได้ครบ
