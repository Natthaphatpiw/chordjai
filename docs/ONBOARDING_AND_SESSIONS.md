# เริ่มใช้ชิดใจให้ง่ายขึ้น และลดเวลารอ LINE

วันที่ 31 ตุลาคม 2026 · Implementation ใน checkout นี้ · การเปิดใช้งานจริงต้องดู deployment และฐานข้อมูลจริงแยกต่างหาก

## ผลิตภัณฑ์ที่เจ้าของเข้าใจได้ในประโยคเดียว

**เล่าเรื่องน้อง แนบรูป แล้วชิดใจช่วยเก็บไว้ให้กลับมาอ่านและดูแลต่อได้**

ไดอารี่เป็นทางเริ่มหลัก ส่วน Passport, สมุดสุขภาพ, Memory book, PetID และ LINE follow-up เป็นเครื่องมือที่เปิดเมื่อมีเหตุผล ไม่ต้องเข้าใจทุกฟีเจอร์ก่อนเก็บเรื่องแรก

| จุดที่ปรับ | พฤติกรรมใหม่ |
|---|---|
| เมนูหลัก | วันนี้ / บันทึก / น้องของฉัน บนมือถือและเดสก์ท็อป |
| วันนี้ | ชวนเขียนหนึ่งเรื่อง พร้อมเรื่องล่าสุดและวันนัดในอนาคต ถ้ามีข้อมูลจริง |
| เพิ่มน้อง | ชื่อและเลือกแมว/สุนัข ส่วนเพศ วันเกิด และทำหมันเปิดเพิ่มได้ ไม่บังคับ |
| เขียนเรื่อง | พิมพ์ข้อความ แนบ/ถ่ายรูปได้สูงสุด 5 รูป วันที่เริ่มเป็นวันนี้ เปลี่ยนได้ |
| รายละเอียดบันทึก | ประเภท ชื่อเรื่อง อาการ คลินิก ค่าใช้จ่าย วันที่ค่าใช้จ่าย และพื้นที่ระบายส่วนตัวอยู่ในรายละเอียดเพิ่มเติม |
| หลังบันทึก | เก็บต้นฉบับก่อน มีทางเลือกช่วยจัดข้อมูล และทำหน้าความทรงจำเมื่อมีรูป |
| เรื่องอาการต่อเนื่อง | จากบันทึกอาการ/พบหมอ/ติดตาม มีปุ่มอัปเดตเรื่องเดิม โดยไม่สรุปเองว่ายังป่วย |
| เตรียมพบหมอ | เปิดจากน้องของฉันหรือบันทึก ยังต้องตรวจและยืนยันก่อนแชร์ |
| เครื่องมืออื่น | รวมเป็นรายการชื่อและคำอธิบายที่น้องของฉัน ไม่วางทุกเครื่องมือบนหน้าแรก |
| LINE | คำทักทายมีตัวอย่างคำสั่งและปุ่มเริ่มใช้ ตอบด้วยกฎ ไม่ใช้ LLM |

ผู้ที่เข้า deep link เรื่องสัตว์หาย, PetID, triage, Agent result หรือ Passport ยังไปงานนั้นได้ ไม่บังคับเขียนไดอารี่ก่อน การเข้าถึงข้อมูลฉุกเฉินไม่ต้องรอ AI

การเลือกรูปสมุดวัคซีนสูงสุด 10 หน้า, PetID หลายรูป/หลายช่วงเวลา, การแก้/ลบ, สมุดหลายหน้า, บทสนทนา Passport และการแชร์ตามสิทธิ์ยังใช้ระบบเดิม ความยินยอมฝึกโมเดลกับ follow-up ยังคงแยกและไม่ถูกเปิดจาก onboarding

## ช่วยจัดข้อมูลหลังบันทึก

`POST /api/v1/health/care/entries/:id/organize` รับ `{version}` และคืนข้อเสนอ ไม่เขียนฐานข้อมูลคลินิกหรือแก้ต้นฉบับ

1. ตรวจผู้เขียน/เจ้าของที่มีสิทธิ์แก้ รุ่นบันทึก และ service consent
2. ส่งเฉพาะ narrative ของบันทึกนี้เข้า `gpt-6.1-sol` ผ่าน client กลางเดิม ไม่ส่งรูปหรือ private reflection
3. รับประเภท อาการ และข้อความคลินิก/การดูแลที่เป็นข้อความคัดตรงจากต้นฉบับ ตรวจหลักฐานซ้ำด้วยโค้ด และตัดข้อมูลที่ไม่มีในต้นฉบับ
4. ค่าใช้จ่ายต้องมีจำนวนเงินและสกุลเงินชัดเจนในข้อความเดียวกัน ไม่ตีความน้ำหนักหรือจำนวนวันเป็นเงิน สถานะจ่ายจริง/ประมาณการให้เจ้าของเลือกเอง วันที่ค่าใช้จ่ายเว้นว่างได้
5. ตรวจสิทธิ์ ความยินยอมและรุ่นอีกครั้งหลัง AI ทำงาน เส้นนี้ไม่ replay private result จาก HTTP idempotency cache
6. เจ้าของนำข้อเสนอไปตรวจ/แก้ในฟอร์มเดิม แล้วกดบันทึกเอง ใช้ version check ป้องกันทับงานที่เพิ่งถูกแก้จากที่อื่น ข้อมูลเดิม รูป ข้อความส่วนตัว และตัวเลือกแชร์ถูกเก็บไว้

ไม่สร้างการวินิจฉัย แผนยา ขนาดยา วันนัด หรือสถานะว่ารักษาเสร็จจากข้อความแผนอนาคต ผล AI ยังอาจจัดประเภทผิดได้ จึงมีขั้นตรวจโดยเจ้าของเสมอ การบันทึกธรรมดาใช้งานได้โดยไม่เรียก AI

ฟีเจอร์ `care.organize` ใช้งบ/token ledger กลางเดิม จำกัด 10 ครั้งต่อผู้ใช้ต่อวัน deadline 15 วินาที มีเพดานงบและ rate limit ทั้งระบบตามเดิม ปุ่มต้องกดเอง ไม่มีการเรียกอัตโนมัติเมื่อเปิดไดอารี่

## LINE login จำเป็นเมื่อใด

LINE login ใช้ยืนยันบัญชีครั้งแรกเพื่อผูกกับ LINE webhook ไม่ใช้ LINE user ID เป็นรหัสผ่าน หลังจากนั้นใช้ session ของชิดใจได้ในเบราว์เซอร์เดิม

เส้นทางก่อนหน้านี้ต้องพึ่ง sessionStorage ต่อแท็บ และเมื่อไม่มี/หมดอายุอาจรอ LIFF SDK, LINE ID verification, friendship verification และการอ่านโปรไฟล์/consents หลายคำขอ

เส้นทางใหม่:

| สถานการณ์ | งานก่อนแสดงพื้นที่ของเจ้าของ |
|---|---|
| มี access bearer ในแท็บ | อ่าน bootstrap รวม pets และ consents หนึ่งคำขอ; token หมดอายุให้ recovery กลางทำครั้งเดียว |
| เปิดแท็บใหม่และเคยจำบัญชี | POST restore หนึ่งคำขอ รวม bootstrap ใช้ HttpOnly cookie ไม่ต้องโหลด LIFF SDK เพื่อเปิดพื้นที่ทั่วไป |
| ครั้งแรกใน LINE/LIFF | SDK ยืนยัน LINE → backend ตรวจ ID → ออก app session และส่ง bootstrap; ตรวจ OA friendship เบื้องหลังด้วย Vercel waitUntil |
| ครั้งแรกในเบราว์เซอร์ทั่วไป | แสดงหน้าเข้าใช้ทันที ไม่ดาวน์โหลด SDK จนกดเริ่มด้วย LINE |
| คุกกี้หมดอายุ/ถูกล้าง/คนละเบราว์เซอร์ | ยืนยัน LINE อีกครั้ง |
| กดออกจากระบบ | เพิกถอนทั้ง cookie session และ bearer ที่อ้าง session นั้น ไม่ auto-login กลับเอง และแท็บอื่นของโดเมนเดียวกันล้างหน้าบัญชีเมื่อได้รับ storage event |

ข้อมูลสุขภาพและเรื่องล่าสุดโหลดหลังแสดงโครงหน้าหลัก ไม่ต้องรอโหลดเครื่องมือทุกตัวพร้อมกัน Health, Care, PetID, Settings และสมุดโหลดตามหน้าที่เปิด SDK init จำกัดรอ 12 วินาที, LINE exchange 20 วินาที, restore 12 วินาที มีข้อผิดพลาดและทางลองใหม่ ไม่ปล่อย spinner ไม่สิ้นสุด

นี่เป็นการลดงานบนเส้นทางเปิดหน้า ไม่ใช่การรับประกันเวลาเปิดจริงในทุกเครือข่าย ต้องวัดบน LINE iOS/Android และอุปกรณ์ผู้ใช้จริง โดยแยกครั้งแรกกับครั้งกลับมา

## การเก็บ session

- Production cookie `__Host-chordjai_owner`: Secure, HttpOnly, SameSite=Strict, Path=/ ไม่มี Domain อายุสูงสุด 30 วันนับจากการยืนยันครั้งนั้น ไม่ต่ออายุเงียบ ๆ ทุกครั้งที่เปิด
- ฐานข้อมูลเก็บ SHA-256 ของค่าลับสุ่ม ไม่เก็บค่าคุกกี้ดิบ LINE ID token หรือ LINE access token
- `identity.web_sessions` เปิด RLS/FORCE RLS และให้ worker เข้าถึง app role อ่าน hash ไม่ได้
- JWT อายุ 1 ชั่วโมงมี `sid`; middleware ตรวจว่า session ยังมีสิทธิ์และบัญชียัง active ใน query ตรวจผู้ใช้เดิม จึงเพิกถอน bearer เก่าได้เมื่อ logout
- การ restore ไม่ rotate cookie ป้องกันคำขอหลายแท็บแย่ง cookie; จำกัด session active สูงสุด 10 อุปกรณ์/บัญชี การสร้างใหม่จำกัด 30 ครั้ง/ชั่วโมงและ 100 ครั้ง/วันต่อบัญชีที่ยืนยันแล้ว และย่ออายุ receipt ของ session ที่เพิกถอนเหลือไม่เกิน 1 ชั่วโมง
- Cookie endpoints ตรวจ Origin ที่อนุญาต รับเฉพาะ POST; Origin ไม่ถูกต้องถูกปฏิเสธก่อนส่ง LINE proof ออกไป
- Login attempt มี nonce และ revoked tombstone ทำให้คำตอบล็อกอินที่มาถึงหลัง logout ไม่คืนสิทธิ์ให้ attempt เดิม
- localStorage เก็บแค่ธงเคยจำบัญชี/ออกจากระบบ ไม่มี refresh token, bearer หรือข้อมูลสัตว์จริง; bearer ต่อแท็บยังอยู่ sessionStorage; bootstrap อยู่หน่วยความจำและถูกทิ้งเมื่อใช้/ออกจากระบบ
- API ตอบ `private, no-store` ไม่ใช้ public CDN cache กับข้อมูลเจ้าของ ผู้ใช้ที่ใช้เครื่องร่วมกันควรใช้ปุ่มออกจากระบบ
- LINE webview, Safari และ Chrome อาจมี cookie jar คนละชุด จึงไม่สัญญาว่ายืนยันครั้งเดียวใช้ได้ข้ามทุกแอปหรือทุกอุปกรณ์ เมื่อเปลี่ยนบัญชี LINE ให้ sign out แล้ว sign in ใหม่
- Scheduler ลบ session ที่หมดอายุเป็นชุด; logout ไม่ลบบันทึกสุขภาพ

## SQL และ environment ก่อนเปิดใช้

ใช้ฐานข้อมูล 27 เพิ่มจาก 26 โดยผู้ดูแลรันเอง:

1. เปิด `supabase/upgrade-26-to-27.sql` และรันครบไฟล์ใน Supabase SQL Editor
2. รันซ้ำได้ สคริปต์ตรวจโครงสร้าง/checksum/รุ่นก่อนเปลี่ยน และรักษาข้อมูลเดิม
3. ตรวจ `supabase/diagnostic.sql` ฉบับปัจจุบันว่ารุ่น 27 และไม่มี schema drift
4. Deploy backend และ owner app รุ่นที่รองรับ session พร้อมกัน ตรวจ `/app`, LINE ครั้งแรก, เปิดซ้ำ และ logout บนอุปกรณ์จริง

**ไม่ต้องเพิ่ม secret หรือ env ใหม่** ใช้ APP_JWT_SECRET, DATABASE_URL, APP_ORIGIN และ ALLOWED_ORIGINS เดิมให้ตรงโดเมนจริง การตั้ง origin เดิมต้องครอบคลุมโดเมนที่เจ้าของใช้งาน เช่น `https://www.chordjai.life` ไม่ใส่ wildcard กับ session Origin

LIFF IDs และ Messaging webhook เดิมไม่ต้องเปลี่ยน หน้า `/app?tab=profile`, `/app?tab=health`, `/app?tab=home&compose=1` เป็น destinations เพิ่มใน navigation ไม่ใช่ LIFF registration ใหม่

หากฐานข้อมูลยังเป็น 26 โค้ดออก access bearer เดิมได้ แต่ยังไม่มี persistent owner cookie; ไม่ควรประกาศว่าแก้การจำบัญชีพร้อมใช้จนตรวจ production schema/deployment จริง

## การวัดและทดสอบกับผู้ใช้ใหม่

บันทึก `app.opened.properties.readyMs` และ `authPath` เป็นเวลาระหว่างเริ่ม auth/bootstrap จนได้ข้อมูลบัญชี ไม่รวมเวลาที่ผู้ใช้ค้างอ่าน consent เป็นหลักฐานฝั่ง client ไม่ใช่ end-to-end network SLO ทั้งระบบ

`authPath` แยก stored_token / owner_session / line และ `care.composer.opened` แยก quick / records โดยไม่ส่งข้อความ รูป ชื่อน้อง หรือรายละเอียดสุขภาพใน properties เหตุการณ์ `pet.created` และ `care.entry.saved` ยังมาจาก backend เหมือนเดิม

ประเมิน:

- ผู้ใช้ใหม่ที่สร้างน้องและบันทึกจริงได้โดยไม่ต้องถามผู้ช่วย
- เวลาจนเก็บเรื่องแรก จำนวนการกดย้อน/ยกเลิก/เปิดผิดหน้า และจุดติดขัดจากการสังเกต
- p50/p95 readyMs แยก authPath, อุปกรณ์และเครือข่ายจากการทดสอบที่ควบคุมได้
- ผู้ใช้กลับมาจดเรื่องต่อ, เตรียมพบหมอ และใช้ประวัติย้อนหลัง มีประโยชน์จริงเพียงใด
- แยกเจ้าของใหม่ ผู้ดูแลร่วม ผู้เข้าเพื่อช่วยสัตว์หาย และผู้ใช้เดิม ไม่รวมทุกกลุ่มเป็น funnel เดียว

ทดลองกับผู้ใช้ใหม่กลุ่มเล็กทั้งไทย/อังกฤษก่อน ตั้งโจทย์ “เพิ่มน้องและเก็บเรื่องวันนี้พร้อมรูป” แล้วให้ทำเองก่อนสอน จับเวลาผ่าน LINE บนเครื่องจริง ไม่ถือว่าชุดทดสอบสังเคราะห์พิสูจน์ conversion หรือ retention แล้ว

## หลักฐานใน checkout

- Unit tests สำหรับ restore ร่วมหลายคำขอ, ไม่โหลด SDK ใน browser ธรรมดา, timeout, cookie หมดอายุ, การออกจากระบบขณะมีคำตอบค้าง และตรวจหลักฐานข้อเสนอ AI
- Isolated PostgreSQL/API tests สำหรับ cookie flags, owner scope/RLS, logout revocation, expiry/suspension/role change, Origin, late-login tombstone และ AI ที่ไม่เขียนข้อมูล/ไม่ส่ง reflection/ตรวจสิทธิ์ซ้ำ
- Full migration tests รวม 26→27→27, compact/full packet race, checksum และ drift rejection พร้อม sentinel preservation
- Browser QA ใช้ข้อมูล demo ใน localhost ไม่มีการส่ง LINE จริงหรือสร้างประวัติการรักษาจริง
